## 1. 用途

快照保存一次运行在两个处理单元之间的全部运行现场（JKRD7 §9.2）：

- 各 JKI 的 q 与 trigger_all；
- 各 JKS 登记的轮记录；
- 各 thread 的两个 FIFO。

一个节点可能同时有多个排队任务，不能从 q 或 trigger_all 反推 FIFO 的内容，所以三部分都要保存。

提出快照的原因（提案 P14）：在主机与 GPU 之间搬运状态，以及在检查点比对两个后端的状态。

## 2. 快照格式

快照是独立的 JSON 文件，不属于 JKM。

快照只在两个处理单元之间保存。事务是一个处理单元，所以快照中不会有进行到一半的事务。定义（JKM）只表示初始状态，所以 JKM 中的 trigger_all 必须全为 null（JKRD7 §3）；运行中的到达记录只保存在快照中。

下例是 M_TX（JKRD7 §10.5）的中间状态：连续注入两次 G1.Q10，第一个事务刚结束。

```json
{
  "snapshot": "S1",
  "jkm": "M_TX",
  "version": "7.0.0",
  "q": {"G1.Q10": 1, "G2.Q101": 1, "G2.Q102": 1, "G2.Q103": 0},
  "trigger_all": {},
  "rounds": {},
  "threads": {
    "work": {
      "events": [],
      "tasks": [{"tx": "G2", "prereqs": ["G2.Q103"]}]
    }
  }
}
```

| 字段 | 内容 |
| --- | --- |
| `snapshot` | 快照名称 |
| `jkm`、`version` | 对应的模型与格式版本 |
| `q` | 全部 JKI 的 q，键为绝对路径 |
| `trigger_all` | 不全为 null 的 all 节点到达记录 |
| `rounds` | 不为空的 JKS 登记轮记录。键为 JKS 绝对路径，值按登记类型列出本轮前置，按首次到达顺序 |
| `threads` | 每个 thread 的事件 FIFO 与任务 FIFO，按 FIFO 顺序 |

FIFO 项的写法：

- 事件：`{"source": 来源}`。
- 节点任务：`{"node": 目标}`。
- 事务任务：`{"tx": 目标 JKS, "prereqs": [本次前置]}`。

事务任务的 prereqs 就是 JKRD7 §5.3 记下的本次前置：transaction 登记到齐的一轮，列出该登记的全部前置，各一次，按首次到达顺序；transaction_any 只列发出通知的那一个前置。

定义加快照，可以从该点继续执行，结果与不中断的运行相同。

### 2.1 各字段的写法

下面是 `checkSnapshot`（[snapshot.ts](snapshot.ts)）按上述规则核对的内容。标“（检查）”的约束只在代码中，规则文字没有写明，见第 6 节。

**顶层**：恰好七个字段，不能多也不能少。

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `snapshot` | 字符串 | 非空（检查） |
| `jkm` | 字符串 | 与模型的 `jkm` 相同 |
| `version` | 字符串 | 只能是 `"7.0.0"` |
| `q` | 对象 | 键是 JKI 绝对路径，值是 0 或 1；列出全部 JKI，不多不少 |
| `trigger_all` | 对象 | 没有记录时写 `{}` |
| `rounds` | 对象 | 没有记录时写 `{}` |
| `threads` | 对象 | 键是 JKM.threads 中声明的名称 |

bit 按 JSON 原文核对，只能写成 `0` 或 `1`（JKRD7 §2 第 2 条）。

**trigger_all 的每一项**：

| 属性 | 约束 |
| --- | --- |
| 键 | 触发模式为 all 的 JKI 的绝对路径 |
| 值 | 数组，与该节点的 `trigger.all` 等长、同顺序 |
| 元素 | `null`（该来源本轮未到达）、`0` 或 `1`（到达时记下的值，JKRD7 §4.1） |
| 只列未齐的记录 | 至少一个元素不是 null，也至少一个是 null。全部到达时节点已触发，记录已清空 |

**rounds 的每一项**：

| 属性 | 约束 |
| --- | --- |
| 键 | JKS 绝对路径 |
| 值 | 对象，键是登记类型，只能是 `all` 或 `transaction`（其他类型不整合，没有轮） |
| 类型下的数组 | 本轮已到达的前置，写绝对路径，按首次到达顺序 |
| 数组约束 | 非空、不重复、都是该登记的前置、个数少于登记的前置数（到齐的一轮已放行） |

**threads 的每一项**：值恰好是 `{"events": [...], "tasks": [...]}`，两个数组按 FIFO 顺序，队首在前，可以为空。

| 项 | 约束 |
| --- | --- |
| 事件 | 只有 `source` 一个键；来源是 JKI 绝对路径 |
| 节点任务 | 只有 `node` 一个键；目标是 JKI 绝对路径，且该节点的 EX 非空（检查） |
| 事务任务 | 只有 `tx`、`prereqs` 两个键；目标是带事务登记的 JKS 的绝对路径；prereqs 是本次前置 |

### 2.2 快照中没有的内容

- 进行到一半的事务。
- 执行记录（JKRD7 §9.4）与已完成的处理单元数：不属于运行现场。
- 模型本身：快照用 `jkm` 名称指向模型，继续运行时另给 JKM。

## 3. 文件文本格式

规则不要求键的顺序。两个后端按下面的写法导出，所以同一现场的快照文本逐字节相同：

- 两格缩进，末尾一个换行（`formatSnapshot`）；
- 顶层按第 2 节的字段顺序；
- `q` 与 `trigger_all` 按 JKRD7 §7.3 的路径顺序；
- `rounds` 先按 JKS 层数，再按路径文本，最后按类型名。

这一格式与原 Python 工具的输出逐字节相同（[TypeScript.md](../TypeScript.md) 第 7 节）。

## 4. 代码

| 文件 | 内容 |
| --- | --- |
| [snapshot.ts](snapshot.ts) | 类型 `Snapshot`；`checkSnapshot`（第 2 节的检查）；`requireSnapshot`（不通过时抛出）；`formatSnapshot`（第 3 节） |
| [cpu.ts](cpu.ts) | CPU 后端：`takeSnapshot(ex, name)` 导出，`loadSnapshot(ex, snap)` 载入 |
| [gpu.ts](gpu.ts) | GPU 后端：`encodeSnapshot`、`decodeSnapshot` 在快照与实例状态区之间转换；`runWithSnapshots` 执行一组可带起始快照的实例，并交回结束时的快照 |

两个后端留给本模块的接口：

- **CPU**（[src/cpu.ts](../src/cpu.ts)）：执行器的 `q`、`triggerAll`、`rounds`、`events`、`tasks` 可读写；`arrivals()` 给出排好序的到达记录与轮记录。[src/executor.ts](../src/executor.ts) 的 `runScriptCpu` 有 `before` 选项，在注入第一批之前调用，用来载入快照。
- **GPU**（[src/gpu/backend.ts](../src/gpu/backend.ts)）：`GpuInstance.start` 是已编码的起始状态；`GpuResult.state` 是运行结束时的状态区，出错的实例为 null；`initState` 写入模型初值。

各后端的行为：

- **CPU**：配合 `step()` 可以在任意两个处理单元之间导出。载入前先检查快照；载入只替换运行现场，执行记录与处理单元计数不变。
- **GPU**：
  - 编码前先检查快照。事务任务的前置是本次前置，所以前置数不会超过任务项留出的位置。
  - 编码时，把事件的来源、节点任务的目标和事务任务的前置换成节点编号，把事务任务的目标换成 JKS 编号；解码时反过来。键的顺序与 CPU 相同，所以快照文本逐字节相同。
  - 只在运行结束时生成快照（见第 6 节 C5）。正在执行事务的实例不是合法的快照点，`decodeSnapshot` 返回 null；运行结束时所有实例都已静止，自然满足。
  - 出错的实例没有快照。
  - 快照中的事件数或任务数超过 GPU 的 FIFO 容量时抛出错误。

命令行：

```bash
node tools/reference.ts --script <运行脚本> [--batch] [--start <快照>] [--save <快照>]
node tools/gpu.ts --script <运行脚本> [--start <快照>] [--save <快照>]
```

- `--start`：载入快照后再按运行脚本注入各批。
- `--save`：运行结束时保存快照，快照名称取运行脚本的 `run`。

展示页（[docs/web-show.md](../docs/web-show.md)）：

- “GPU 执行并对拍”之后可以切换显示某个 GPU 实例的结果，它的 q、到达记录、轮记录与 FIFO 取自结束时的快照。
- 时间轴的后退与跳转靠从初值重放，不用快照。
- 页面还没有快照窗口，不能捕获、下载、载入或恢复快照。用户 2026-11-08 决定延后；2026-11-11 交给定时任务 `snapshot-daily` 处理（见第 6.4 节）。

## 5. 验收

| 条款 | 预期行为 | 核对 |
| --- | --- | --- |
| 快照格式 | 字段多出或类型不对、jkm 与模型不对应、到达记录或轮记录不合法、事件项或任务项不合法（含事务任务的前置不是本次前置）均被拒绝 | `node tools/validate.ts`：正例 2、负例 23（[src/testing/static.ts](../src/testing/static.ts)） |
| 本文的示例 | 第 2 节的 JSON 块对照 JKRD7 正文中的 M_TX 通过检查 | `node tools/validate.ts` |
| 快照（CPU） | M_TX 的中间状态与第 2 节一致；从快照继续的记录与不中断运行相同；随机模型 150 次中途快照同样相同 | `node tools/reference.ts` |
| 结束时的快照（GPU） | GPU 各项对拍中，结束时的快照文本与 CPU 逐字节相同 | `node tools/gpu.ts` |
| 从快照继续（GPU） | 第 2 节的 M_TX 快照与随机模型 150 次中途快照（其中 45 次带未处理的事件或任务）载入 GPU 后继续运行，执行记录与结束快照与 CPU 逐字节相同 | `node tools/gpu.ts` |
| 命令行 | JKRD7 §9.4 的脚本用 `--save` 保存的快照、`--start` 继续运行的记录，两个后端逐字节相同 | 手动核对，不在自动检查中；2026-11-11 移动代码后 CPU 一侧重新核对过 |

这些检查通过，只说明在本机已核对的范围内实现与本文一致。不说明恢复流程、多 thread 或其他浏览器、其他 GPU 已经验证。批执行模式（`--batch`）下从快照继续没有验收案例。
