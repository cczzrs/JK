## 一、事务边界

### P10 事务范围内的成员只在事务中执行

**问题。** §6 把 R(G) 称为“事务范围”，§5.3 说受整合订阅者“只在该事务任务中接收”。但现行规则下，范围内的成员还有三条路径可以在事务之外执行。静态检查都放行，执行时也不报错。

| 路径 | 试探结构 | 结果 |
| --- | --- | --- |
| 1. 同一 JKS 混用其他登记类型 | G1 登记 transaction=[Q1] 和 any=[Q2]；Q2 触发范围内的 Q3，Q3 再触发 Q4 | 注入 Q2 后没有事务任务，Q3、Q4 作为普通节点任务在事务外执行 |
| 2. 祖先 JKS 用 all 登记范围内的成员 | G1.G1 是事务 JKS；祖先 G1 登记 all=[Q2, G1.G1.Q2] | 先注入 Q1 再注入 Q2 时，G1 的 all 在事务外到齐，范围内的 G1.G1.Q3 被放行到事务外执行 |
| 3. 范围内有输入入口 | 事务 JKS G1 的子结构 G1.G1 登记了入口 G1.G1.Q1；它在 G1 的范围内 | 注入 G1.G1.Q1 后，范围内的 G1.Q2 在事务外执行 |

**建议条文**（加入 §6.2）：

> 事务范围内的成员只在事务中执行。为此：
> - 具有 transaction 或 transaction_any 登记的 JKS，不再使用其他登记类型；
> - 祖先 JKS 登记位于该 JKS 内的成员时，只能用 transaction 或 transaction_any；
> - 事务范围内不得有输入入口，输入入口只能是事务 JKS 的前置成员。

这三条足够保证上面的性质。理由如下：

- §6.2 已经规定，范围内成员只被本 JKS 的成员触发。
- 前置成员的通知只经事务登记进入范围。
- 范围内成员的通知只在事务中产生。
- 子孙 JKS 的登记位于范围之内，不会把成员带到事务之外。

现有示例和十选一附件都满足这三条，不需要改动。

**需决定：**
- **A（推荐）**：加入这三条约束，静态检查拒绝违反的结构。
- **B**：允许这些结构，并在 §6 写明“经这三条路径进入范围的通知在事务之外处理”。

## 二、终止与调度

### P11 纯通知环

**问题。** §6.2 允许事务范围以外成环，并且“是否终止由结构自身负责”。但有一种环必然不终止，还会拖住整个模型：环上的节点都是 any 触发、空 EX，并且按自己的 q 会发布。

- 空 EX 节点的 q 永远不变，所以它每次被触发时的发布判定都一样。只要发布过一次，就会一直发布。
- 按 §7.2 事件优先，事件 FIFO 永不为空，任务 FIFO 里的任何任务都得不到执行。受影响的是整个模型，包括与这个环无关的结构。

**试探。** G1.Q2 与 G1.Q3 都是空 EX，互相触发；另有一个与环无关的节点 G1.Q4，由同一个输入触发并带有 EX。注入一次输入后，执行了 5000 个处理单元，Q4 一次都没算，任务 FIFO 一直停着它的任务。

环上只要有带 EX 的节点，就不会出现这个问题：任务按 FIFO 轮流执行，其他结构照常推进。

**建议条文**（加入 §6.2）：

> 由 any 触发、空 EX、按其 q 会发布的节点组成的触发环，并且环上的连接都不经 all、transaction 或 transaction_any 整合，称为纯通知环。纯通知环永不终止，并会使整个模型的任务得不到执行，静态检查拒绝。

**需决定：**
- **A（推荐）**：静态拒绝纯通知环。
- **B**：不拒绝，只在 §6.2 写明这种环的后果。

## 三、CUDA 迁移需要的接口

### P12 可并行批

**问题。** §7.5 要求并行实现的结果与串行参考一致，但没有说明哪些计算可以并行。串行规则下，任务一个接一个执行，后一个任务读得到前一个任务写入的 q。如果简单地把一批任务同时计算，读到的值就可能不同。

**结论。** 下面的条件足以保证并行结果与串行相同，不需要改动任何语义：

> 事件 FIFO 为空时，从任务 FIFO 队首起连续取若干个节点任务，如果
> 1. 它们的目标互不相同，并且
> 2. 每个任务的 sources 都不含排在它前面的任务的目标，
>
> 就可以用这批任务开始时的 q 同时算出全部 result。然后按任务顺序逐个处理：判定 publish、写入 q、投递它的通知，直到事件 FIFO 为空，再处理下一个。
>
> 事务任务单独成批；事务内的局部序列按同一条件分批。

**为什么成立。**
- 投递通知时不写 q，只追加任务和事件、更新到达记录。空 EX 节点的 q 也从不改变。
- 所以同一批任务之间的唯一联系就是 q 的读写，而条件 1、2 排除了这种联系。
- 逐个写入、逐个投递的顺序与串行完全相同。输出模块在投递第 k 个任务的通知时读取 q，读到的正是前 k 个任务写入后的状态。

**试探。** 我按这个条件写了一个批执行器，与参考解释器比对执行记录：

| 对象 | 结果 |
| --- | --- |
| 第 10 节的全部模型 | 记录完全相同 |
| 300 个随机生成的模型（含 any、all、seed、七种 publish、自引用） | 0 个不同；共 1393 批，平均每批 2.4 个任务，最大 7 个 |
| 十选一，事务内也分批，200 组随机输入 | 0 组不同 |
| 十选一单次请求 | 8 个节点任务只需 2 批（每批 4 个）：先算四对配对节点，再算四个位节点 |

**需决定：**
- **A（推荐）**：写入 §7.5，作为“允许的并行方式”；参考工具增加批执行模式，并与串行对拍。
- **B**：只写进实现说明文档，不进正文。
- **C**：不写。

### P13 运行脚本与执行记录

**问题。** §7.5 要求“可观察的结果一致”，但比对还缺三样东西：

- **输入时序**：参考解释器可以在任意处理单元之后注入输入，并行实现没有“处理单元”这个粒度，无法照做。
- **输出观察**：观察哪些通知、读取哪些成员，现在硬写在工具代码里（§9.3 第 5 项待补充）。
- **记录格式**：“q 写入序列和通知序列”是逐节点比，还是比一条全局有序记录，正文没有说清。

**建议。** 增加一种运行脚本。它不属于 JKM，模型本身不增加字段：

```json
{
  "run": "ascii-overlap",
  "model": "assets/ascii-bit-design/digits.jkm.json",
  "observe": {
    "watch": ["G1.Q24"],
    "read": ["G1.Q11", "G1.Q12", "G1.Q13", "G1.Q14", "G1.Q25", "G1.Q26", "G1.Q27", "G1.Q28"]
  },
  "batches": [["G1.Q1", "G1.Q2"], ["G1.Q10"]]
}
```

- `observe.watch` 是输出模块订阅的成员；它们的通知投递时，按顺序读取 `observe.read` 中各成员的 q。
- `batches` 是输入的时序（见下面的选项）。
- 执行记录是一条全局有序记录，按串行顺序排列，只含四种条目：

```json
{"inject": "G1.Q1"}
{"notify": "G1.Q11"}
{"q": "G1.Q15", "from": 0, "to": 0}
{"output": "G1.Q24", "values": [0, 0, 1, 1, 0, 0, 0, 0]}
```

- 事务内产生的通知，按产生时的顺序记录；输出在提交后的投递时记录。
- 处理单元编号、事务开始和提交等属于实现细节，不进记录。
- 并行实现必须产生完全相同的记录。

**输入时序，需决定：**
- **A（推荐）**：按批注入。模型静止时，把一批输入按顺序追加到事件 FIFO，运行到静止，再注入下一批。重叠请求就放在同一批。这对 GPU 最自然：一直算到空闲，再取下一批输入。
- **B**：另外允许“第 k 个处理单元之后注入”。这样能表达任意交错，但并行实现必须能定位到串行的处理单元。

### P14 运行现场快照

**问题。**
- §9.3 第 4 项“运行现场的持久化与恢复格式”待补充。CUDA 实现需要它：在主机与 GPU 之间搬运状态，以及在检查点比对状态。
- 现在定义里的 JKI.runtime.trigger_all 可以写 0 或 1，而 JKS 的轮记录和两个 FIFO 却没有地方写。试探显示：定义中写 trigger_all=[0,null] 的 all 节点，只注入第二个来源就会触发。所以“定义”与“运行现场”的界线不清。

**建议。**
- **定义只表示初始状态**：JKM 中所有 trigger_all 必须全为 null。
- **运行现场另存为快照**，只在处理单元之间保存。事务是一个处理单元，所以快照里不会有进行到一半的事务。在串行语义下，以下四部分就是全部状态：

下面是 M_TX（§10.5）的一个真实中间状态，由参考解释器取得：输出模块订阅 G2.Q101，连续注入两次 G1.Q10，第一个事务刚提交。

```json
{
  "snapshot": "S1",
  "jkm": "M_TX",
  "version": "7.0.0",
  "q": {"G1.Q10": 1, "G2.Q101": 1, "G2.Q102": 1, "G2.Q103": 0},
  "trigger_all": {},
  "rounds": {},
  "queues": {
    "work": {
      "events": [{"source": "G2.Q101", "to": [], "out": true}],
      "tasks": [{"tx": "G2", "prereqs": ["G2.Q103"]}]
    }
  }
}
```

| 部分 | 内容 |
| --- | --- |
| `q` | 全部 JKI 的 q |
| `trigger_all` | 不全为 null 的 all 节点到达记录 |
| `rounds` | 不为空的 JKS 登记轮记录，键为 JKS 绝对路径，按首次到达顺序列出前置 |
| `queues` | 每个 queue 的两个 FIFO。普通事件项只有 `source`。事务提交的事件项另带 `to`（范围外的 JKI 接收者）和 `out`（输出模块是否接收）。节点任务记 `node`，事务任务记 `tx` 与本次 `prereqs` |

- 定义＋快照可以从任意处理单元之间继续执行。
- 并行实现可以在每批结束时与串行快照比对。

**需决定：**
- **A（推荐）**：定义中 trigger_all 全为 null，并采用上述快照格式。
- **B**：只要求定义中 trigger_all 全为 null，快照格式暂缓。
- **C**：都暂缓。

## 四、字段与小修

### P15 pro.jksid 改为管理 JKS 的绝对路径

**问题。** pro.jksid 写的是“管理该节点的 JKS id”。JKS id 改为按层递增的 G 编号之后，G1 在每一层都可能出现，jksid 就不再能确定是哪个 JKS。试探中，一个节点写 jksid="G1"，而模型里同时有 G1 和 G1.G1，静态检查照样通过。

**需决定：**
- **A（推荐）**：jksid 改为管理 JKS 的绝对路径（如 G2.G1），静态检查要求它解析到实际 JKS。
- **B**：暂时删除 jksid，等工厂按本版语义重新设计时再定。

### P16 小修（可逐条批准）

1. **“递增编号”的静态含义。** §3 和 §5.1 写“按递增编号分配”，但第 10 节的示例有 Q101—Q103、Q201、Q202。建议写明：静态检查只要求同层唯一；编号怎样分配、删除后是否复用，由生命周期模块规定。
2. **事务提交的事件进入哪个 queue。** §6.3 只写了“追加到事件 FIFO”。建议写明：进入来源 JKI 所属 JKS 的 queue，与 §7.4 一致。

## 五、示例

### P17 1 bit 寄存器（M_REG）

**问题。** §9.1 说“一个 bit 用‘置 0’‘置 1’两个入口，值由结构内的成员保存”，但没有示例。通知不带值，所以保存一个 bit 需要用到十选一里的配对技巧。这是最基本的结构，值得单独给出。

**建议示例**（试探已验证）：

```json
{
  "jkm": "M_REG",
  "version": "7.0.0",
  "queues": ["work"],
  "roots": [
    {
      "id": "G1",
      "members": [
        {"id": "Q1", "q": 1, "trigger": {"any": []}, "pro": {"tag": ["set0"]}},
        {"id": "Q2", "q": 1, "trigger": {"any": []}, "pro": {"tag": ["set1"]}},
        {"id": "Q3", "q": 0, "trigger": {"any": ["Q1"]}, "sources": {"seed": 0, "s": ["Q4"], "ex": ["K"]}},
        {"id": "Q4", "q": 0, "trigger": {"any": ["Q2"]}, "sources": {"seed": 1, "s": ["Q3"], "ex": ["K"]}},
        {"id": "Q5", "q": 0, "trigger": {"any": ["Q3", "Q4"]}, "sources": {"seed": 0, "s": ["Q3", "Q4"], "ex": ["K", "K"]}, "pro": {"tag": ["value"]}}
      ],
      "trigger": {"transaction_any": ["Q1", "Q2"]},
      "queue": "work",
      "pro": {"tag": ["register"]},
      "runtime": {}
    }
  ]
}
```

- **置 0**：Q3 计算为 Q4 的值，于是 Q3 XOR Q4 = 0。
- **置 1**：Q4 计算为 Q3 的反值，于是 Q3 XOR Q4 = 1。
- Q5 读出这个异或值。

依次输入 set1、set1、set0、set0、set1、set0，输出为 1、1、0、0、1、0。

**需决定：**
- **A（推荐）**：作为 §10.8 加入，并加入参考工具的验收案例。
- **B**：不加。
