## 为什么要补

当前 JKRD7 把几件**直接决定计算结果**的事交给了尚未定义的队列模块，包括：事件和任务谁先处理、一条通知投递给多个订阅者的顺序、JKS 登记怎样控制成员、事务内部按什么顺序推进。所以同一份 JSON 可能算出不同结果。

仓库里的十选一参考核对已经出现了实际后果：数字 0 的请求还没处理完就来了数字 1，B0 输出成了 `1,1`，正确应为 `0,1`。事件优先和任务优先两种调度都会出错（共 4 个重叠反例）。

各项的分工：

- P1–P4 是补齐语义所需的最小集合。
- P5–P7 是接口和小修。
- P8–P9 是文档和工具，在语义确定之后再做。

## 一、JKS 登记的“整合”语义

### P1 整合模型：前置通知怎样进入结构

**问题。** JKS.trigger 现在只写了“到齐后触发任务入队”，没写前置通知和成员 JKI.trigger 是什么关系。以 §9.5 为例，Q103 既登记在 transaction 里，又出现在 Q101.trigger.any 里。如果照常投递，Q101 会在事务之外形成一个独立任务。你已经确认“前置通知是整合出来的”，但“整合”本身还没有条文。另外，JKS.all 到齐后到底放行什么，也还没定义。

**建议条文。**

> 登记在 JKS.trigger 某类型下的前置成员 P 发出通知后，投递分两种情况：
> - 订阅者是**本 JKS 内（含子 JKS）的非前置成员**：由登记类型整合；
> - 订阅者在**本 JKS 以外**：照常投递，不受整合影响。
>
> 各类型的整合方式：
> - **any**：每条通知立即放行，与直接投递相同。any 登记只声明入口，不改变行为。
> - **all**：按轮收集。本轮到齐时，按各前置本轮首次到达的顺序，每个前置放行一次通知给它在本 JKS 内的订阅者；本轮的重复通知不再放行。
> - **transaction**：按轮收集。到齐时形成一个事务任务（见 P3），由事务任务把每个前置的一次通知交给本 JKS 内的订阅者处理。
> - **ack、pre、post、comp、frame 等其他用途**：在单独定义行为之前，按 any 处理。

**例子。** 设 `all=[P1,P2]`，连接为 P1→S1、P2→S2。S1 和 S2 都要等 P1、P2 本轮都到齐后才收到通知。这就是“同步”：让多个分支在同一时刻对齐。JKI.all 只能在单个节点上等待，做不到这一点。

**需决定：**
- **A（推荐）**：采用整合模型。
- **B**：采用别的理解。请说明 JKS.all 到齐后放行的是什么对象。

### P2 任一入口触发的事务（十选一需要）

**问题。** transaction 要求全部前置到齐。十选一这类“多个入口任选一个”的结构因此建不了事务。通知又没有载荷，“选了哪个入口”只能靠哪个入口发出通知来表达，不能先把十个入口合并成一个前置成员再登记。上面那 4 个重叠反例，就是缺少这项能力造成的。

**建议。**
- 新增一个按需类型，名称待定，例如 `transaction_any`。
- 所登记的前置中，任何一个的通知到达，就形成一个事务任务。每条通知各形成一个，不合并。
- 其余规则与 transaction 相同。
- 十选一改为 `transaction_any=[Q1,…,Q10]`，替代现在的 any 登记。这样每次请求的 8 个输出位和完成通知都在一个事务任务内算完；重叠的请求按任务 FIFO 顺序逐个处理，结果与逐次单独输入相同。

**需决定：**
- **A（推荐）**：增加该类型，并请你定名。
- **B**：不增加。十选一不保证请求重叠时的正确性。

### P3 事务任务的执行

在已批准的规则基础上补齐以下几点。已批准的规则是：前置成员不属于事务、按 publish 结果沿连接传播、处理完成后统一提交、多实例顺序执行。

**P3-1 事务范围。** 指登记该事务的 JKS 内（含子 JKS）除前置成员以外的全部成员。每次实际处理的，只是本次通知推进到的那些成员。

**P3-2 事务内部顺序。**
- **A（推荐）**：内部顺序在语义上与全局一致。
  - 事务任务内有自己的事件序列和任务序列，按 P4 的同一调度规则、同一套 JKI 规则（any/all、EX、publish）推进，直到两个序列都为空。
  - 订阅者在范围内：在事务内处理。
  - 订阅者在范围外（包括本 JKS 的前置成员和外部节点）：通知先暂存，事务结束时按产生顺序一次性追加到全局事件 FIFO。这就是“统一提交所需传播通知”中“所需”的确切含义。
  - 这样事务内外用的是同一套规则，不需要另设特例。
- **B**：按触发连接的拓扑顺序处理，每个成员最多处理一次。需要另外规定“同一成员被多个上游触发时怎样合并”。

  采用 A 时，§6.4 里“不附带……内部事件队列”这句话要改：它原本针对的是旧格式，与 A 并不矛盾，但容易被误读。

**P3-3 范围约束。**
- 范围内成员的 JKI.trigger 只能引用本 JKS 内的成员；外部上游只能接到前置成员上。否则外部通知会在事务之外直接触发范围内的成员。
- 范围内的触发连接不得成环，否则事务不会结束。
- sources 只负责取值，不受这两条限制。

**P3-4 任务身份。** 事务任务以登记它的 JKS 的绝对路径为目标，进入该 JKS.queue 对应的任务 FIFO。

**P3-5 嵌套。** 处在活动的祖先事务中时，子 JKS 的登记照常判定 any/all/transaction 条件。条件满足时，就在当前事务内就地处理，不另外入队；条件未满足的轮次记录保留到以后。

**P3-6 “不处理”的任务。** 任务 FIFO 中不被处理的任务（例如目标已被生命周期模块删除）不改变任何 q，也不提交任何通知。哪些情况算“不处理”，由生命周期模块规定。

**需决定：** P3-2 选 A 还是 B；P3-1、P3-3 到 P3-6 是否同意。

## 二、执行模型

### P4 串行参考语义

**问题。** §3.2 写的是“最新可见 q”，§4.3 把“两个 FIFO 的优先级、广播顺序”交给了队列模块。但这些会直接改变计算结果。参考工具对事件优先、任务优先两种策略都跑了一遍，说明这件事还没确定。

**建议条文（写入新的“执行模型”一节）：**

**P4-1 处理单元。** 一次只处理一个单元：要么投递一条事件，要么执行一个任务。一个单元处理期间不穿插其他单元。因此“最新可见 q”就是执行入口时的当前 q，正文措辞随之改为“执行入口时的当前 q”。

**P4-2 两个 FIFO 之间的顺序：**
- **A（推荐）**：事件优先。事件 FIFO 不为空时先投递事件，为空时才执行一个任务。这样同一波通知先全部完成触发判定，再开始计算，行为接近“按波次推进”，将来也便于在 CUDA 上按批并行。
- **B**：任务优先。
- **C**：其他规则。

**P4-3 一条事件投递给多个订阅者的顺序：**
- **A（推荐）**：按订阅者的绝对路径排序，逐段比较，Q 编号按数值比较。这样顺序与 JSON 的书写顺序无关，符合“members 的排列不是计算步骤表”这条原则。
- **B**：按 JSON 中的声明顺序（深度优先）。这样 members 的排列会影响结果。

**P4-4 并行实现（CUDA）的约束：**
- **A（推荐，先定为基线）**：任何并行实现，可观察的结果（各节点 q 的序列、通知序列）都必须与本串行参考语义一致。
- **B**：允许并行实现产出“某一个合法串行顺序”的结果，即可串行化。并行空间更大，但结果不再唯一。

**P4-5 多个 queue 名。**
- 每个 queue 名对应一对 FIFO（事件 FIFO 和任务 FIFO）。
- 节点的任务和事件进入它最近所属 JKS 的 queue；事务任务按 P3-4 处理。
- 不同 queue 之间怎样调度，由队列模块规定。
- 队列的存储、容量、故障处理仍归队列模块。

## 三、接口

### P5 外部输入只注入通知

**问题。** §11 只写了“外部值如何进入可读节点 q”待定。参考工具的实际做法是：上游节点的 q 固定不变，只注入通知；十选一用“哪个入口发出通知”来表达输入值。

**建议。**
- 输入接入模块只做一件事：以某个输入 JKI（any=[]，不由结构内连接触发）作为来源，向事件 FIFO 追加一条通知。它不直接写 q。
- 输入值用独热入口表达。例如一个 bit 用“置 0”“置 1”两个入口，值由结构内的成员保存，做法与十选一相同。
- 输出接入模块订阅输出成员的通知，在投递时读取该成员的 q。

**需决定：**
- **A（推荐）**：只注入通知，不新增写 q 的通道。
- **B**：允许输入模块直接写 q 再注入通知。需要另外规定写入时机和它与任务的先后关系。

### P6 最小 JKM 模型封装

**问题。** 现在有三样东西没有载体：
- 多个根结构（如 G_PRE、UPSTREAM、G_PARENT）放在哪里；
- JKS.queue 引用的“已声明队列”在哪里声明；
- 模型的版本标记写在哪里。

**建议格式：**

```json
{
  "jkm": "M1",
  "version": "7.0.0",
  "queues": ["work"],
  "roots": []
}
```

- `roots` 里放完整的根 JKS 对象。绝对路径从根 JKS 的 id 开始写，JKM 的 id 不进入路径。
- `queues` 声明全部 queue 名，JKS.queue 必须引用其中之一。
- JKI 编号的作用域统一为“当前 JKS”，因为 JKM 不直接包含 JKI，现文中的“当前 JKS／JKM”随之改写。
- 队列现场和恢复格式另行规定。

**需决定：**
- **A（推荐）**：采用。
- **B**：调整字段后采用。
- **C**：暂缓。

### P7 小修（可逐条批准）

1. **sources.seed** 只能是 0 或 1，写 null 视为非法。现文只说“null 不等于缺失”，没说明它到底是什么含义。
2. **JKS id** 不得写成“Q＋数字”的形式，避免和同层 JKI 的短 ID 混淆。
3. **事务以外的连接允许成环**。计数器、振荡器都是正常用法，是否终止由结构自己负责；事务范围内仍按 P3-3 禁止成环。
