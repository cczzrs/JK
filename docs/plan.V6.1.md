# JK CUDA 实现方案 V6.1

> 状态：本文是设计与实现方案，CUDA 内核、运行时和恢复实现尚未编写或在 GPU 上验证。已确认的设计不等于已经实现或测得性能。

> 本次修订：按用户最新明确要求，删除组内多个调用并行和外部输入直接形成事件。所有模型任务先进入 FIFO；同一实例每次只执行一个任务，完成本任务的事件传播、目标匹配和所形成任务的正式入队后，才结束本任务并重新选择 FIFO。此前与此冲突的执行组、后续组分区和跨任务并行规则不再适用。

## 1. 目的、范围和阅读方式

本方案面向单个大型 JK 模型、单张 NVIDIA GPU，采用 PyTorch CUDA 张量、自定义 C++/CUDA 内核及必要的宿主 I/O 和资源管理。JK 规则是设计来源；CUDA 用于实现完整的 FIFO 任务执行与事件传播流程。用户最新明确的任务边界优先于本方案此前允许的多调用并行设计。新运行 profile 与 V5 兼容 profile 分开定义，不能把新行为称为旧 JKRD 已有规则。

本文按“模型和输入任务入队 → 选择一个 FIFO 队首任务 → 读取参数及执行 → 提交和判断发布 → 事件传播、触发匹配及目标任务入队 → 本任务结束 → 重新选择 FIFO”组织。第 3 节定义两类工作与两个逻辑队列，第 4 节说明完整循环的性能设计，后续模块落实事务、结构、I/O 和恢复。各模块保留树形图、方案列表、边界和验收点；原 V6 的 A01–H04 对照见第 11 节。标注空白用于记录问题或验收结果，不表示需要重新批准已确认的方向。

来源基线为用户提供的 `plan.V6.md` 及其引用的 `DRAFTS--V5.0.0@0a8cc58c882dac1b1c1af21b304cb18c7afe2010`。其中 V5 的 75 任务、六个检查点是候选设计及人工推导，不代表 CUDA 执行或恢复已验证。会话批准的其他功能继续保留，但执行顺序以本次明确的 FIFO 完整任务边界为准。

## 2. 全局结构与运行流程

```text
JK CUDA 实例（单张 NVIDIA GPU）
├─ 模型和编译
│  ├─ 逻辑节点：程序模板 + 来源绑定 + 可选状态槽 + 触发契约
│  ├─ 计算连接与触发订阅分开；稳定 ID／世代映射到设备槽位
│  └─ 校验 → 编译或解释 → GPU SoA 数组、稀疏连接和页池
├─ 接入与 FIFO 排队
│  ├─ 外部数据／ACK／业务控制／结构请求 → 校验、锁存、形成任务
│  ├─ 为任务登记 FIFO 归属、入队次序和载荷所有权
│  └─ accepted / device_visible / durable 分别报告；传输就绪不触发传播
├─ 每实例唯一活动任务
│  ├─ 按队列选择规则领取一个 FIFO 队首
│  ├─ 绑定本任务参数和状态 → 执行 EX／声明的任务程序 → 提交
│  ├─ 按发布条件将本任务事件写入 event_queue
│  ├─ 传播工作者：事件出队 → 订阅展开 → 目标匹配 → 新任务入 FIFO
│  └─ 本任务全部事件处理完成且新任务入队可见 → 结束 → 重新选队列
├─ 更快运行两个任务队列
│  ├─ 传播阶段：当前任务的扇出并行、输入匹配和批量入队
│  ├─ EX 阶段：当前任务的参数访问、指令优化、提交与事件形成
│  └─ 阶段交接：入队／出队、发布可见性、FIFO 顺序和完成判定
├─ 业务模块
│  ├─ 可配置帧宽与存储块、前后业务接入、帧世代与 ACK
│  ├─ FIFO 任务执行动态创建、连线、改 EX、退休回收
│  └─ 事件反馈环、依赖环检查和预算监督
└─ 对外交接与运行保障
   ├─ 已提交输出 → D2H → 宿主 outbox → 应用接收／回调
   ├─ 背压、唯一活动任务的失败保留与显式重试
   ├─ 完整任务边界快照 + 可选持久日志／输出箱
   └─ 兼容 profile、独立参考、真实 GPU 正确性和性能验收
```

**已确认的关键行为：**所有独立模型任务先排 FIFO；同一实例最多一个活动任务；任务执行时绑定状态和 q_seed；该任务的提交、全部事件传播、目标匹配和新任务入队完成后才能结束；传播期间产生的新任务只排队，不立即执行；外部输入可以随时接纳和准备载荷，但不能绕过输入任务自行传播。多 FIFO 的队列选择与队内 FIFO 是两层规则，不自动改成一个全局 FIFO，也不擅自增加公平轮转。

单次任务内部允许使用多个 CUDA 线程处理参数、位运算或传播扇出；这些线程不代表多个独立任务同时执行。保持四种触发模式、同 key 同来源 FIFO、帧身份和 ACK 绑定、动态结构、可选持久化等其他设计。对相同模型版本、逻辑入队记录和任务选择记录，改变 CUDA block、传播分块和 stream 时序不得改变逻辑轨迹。真实异步接入可能改变正式入队的先后，应记录该顺序后再进行等价重放。

## 3. CUDA 两类执行工作与双队列

### 3.1 两类工作与完整闭环

**方案 Q01：两类工作角色，围绕同一个活动任务顺序协作。** “任务执行工作者”与“事件传播工作者”是 CUDA 程序职责，不是两种物理 CUDA 核。kernel 是执行程序；一个任务可以跨多个 kernel 完成，也可由有界常驻程序分阶段推进。kernel 返回或 EX 算完均不等于逻辑任务结束。

```text
外部输入／控制请求 ──锁存、登记──→ 对应 FIFO 的 task_queue
                                               ↑
                         传播形成的目标任务 ────┘
                                               │
                              当前没有活动任务时选择一个队首
                                               ↓
                                      唯一 active_task
                                               ↓
                        读取本任务参数／状态 → EX／任务程序 → 提交
                                               ↓
                                         判断是否发布事件
                          ┌────────────────────┴───────────────┐
                        不发布                               发布
                          │                                    ↓
                          │                      event_queue（归属当前任务）
                          │                                    ↓
                          │                     读取订阅 → 展开目标 → 匹配输入
                          │                                    ↓
                          │                     形成新任务并正式追加对应 FIFO
                          │                                    ↓
                          │                     本任务全部事件和投递处理完成
                          └────────────────────┬───────────────┘
                                               ↓
                       核对提交、传播与入队完成 → 结束本任务 → 重新选择 FIFO
```

| 工作类别 | 消费内容 | 完成的工作 | 调度约束 |
|---|---|---|---|
| 任务执行 | 选中的唯一 FIFO 队首任务 | 参数／状态绑定、EX 或声明的任务程序、提交、按条件生成事件 | 当前任务未结束，不领取或执行另一个独立任务。 |
| 事件传播 | 当前任务已经发布的事件记录 | 订阅读取、扇出展开、目标输入匹配、形成并追加目标任务 | 目标任务只入队；本次传播不递归调用目标 EX。 |

**结构约束。** 每个合法任务、事件、订阅投递、触发、提交和队列记录保留独立身份。不得跨节点直接调用、删除传播、合并同值事件或把多个独立任务包装成一次计算以绕过 FIFO。可以批量写入当前传播形成的多条任务记录，但不能因此批量执行这些任务。

#### 完整任务边界与队列选择

1. 任务状态依次经过 `QUEUED → ACTIVE → EXECUTED/COMMITTED → PROPAGATING → COMPLETE`；不发布事件时跳过传播阶段。等待资源和失败保留是活动任务的暂停状态，不是完成状态。
2. 每条任务 FIFO 按正式入队顺序追加，按队首领取。若 profile 定义多条 FIFO，只有当前任务结束后，才重新按该 profile 的队列选择规则选一个队首。旧 V5 兼容 profile 保留 `Xi→RAM→Qi` 的原规则；新 profile 的具体队列归属和优先策略必须显式注册，不能从物理分片推断。
3. 外部输入、ACK、会改变模型状态的完成控制记录和结构更新请求均先形成相应任务并排队。宿主接纳、H2D、JIT 编译和页池准备可以并行进行，但不执行排队任务的模型效果。
4. 输入任务与传播生成的任务若追加同一 FIFO，通过受控的逻辑入队入口登记顺序。传播形成的一批任务先按事件内和订阅内的规定顺序定位，再正式追加；不能让各 CUDA 写入线程抢位决定这些目标任务的次序。记录实际入队线性化顺序用于重放，不另设隐含的“内部优先”或“外部优先”。
5. 入队位置的预留与记录发布分别管理；载荷尚未可读或记录尚未写全的队首不能被同队后项越过。选中任务后需要等待传输或资源时，保留该活动任务，不转而执行另一个模型任务。
6. 本任务完成必须同时满足：执行和提交达到其正常终止状态；全部应发布事件已经生成；其全部订阅投递已处理；目标匹配已完成；形成的新任务已完整写入并正式入 FIFO；相关工作者不再持有未完成投递。只看到 `event_queue` 暂时为空或事件已经入队都不足以判定完成。
7. 目标输入未齐时，把已到达 token 留在触发状态中即可结束这次投递。当前任务不等待目标未来收齐，也不等待新入队任务执行；否则会阻止后续 FIFO 任务提供缺失输入。
8. 单个任务失败或传播中遇到资源等待时保留唯一活动现场。重试继续原任务；只有本任务真正完成，才重新选择 FIFO。补页、同步、保存现场和显式重试属于执行器管理动作，不应排在被它们解除阻塞的模型任务之后。

### 3.2 公共定义：节点、来源和输入

**方案 N01-1：统一计算 IR，状态存储外置。**

```text
基础计算：r = (q AND a) XOR b
J(x)：a=x，b=0       → q AND x
K(x)：a=1，b=x       → q XOR x

逻辑节点 = 程序模板 + 来源绑定 + 可选状态绑定 + 触发契约
```

1. 状态节点的起点从绑定状态槽读取；无状态计算可使用常量或其他值作为起点。普通计算中间值留在寄存器，不强制为每个算子建立全局状态槽。
2. J/K 指令可紧凑表示为 `(op, source_index)`，无需逐条存储 J 的常量 b 或 K 的常量 a。计算 IR 是加载／编译阶段分析 EX 的中间表示；可选择直接 AND、XOR 或合适的三输入布尔指令，不强制生成 a、b 中间数组。`LOP3` 可表达一个三输入布尔函数，不等于必定执行两条 AND／XOR；最终指令以目标 GPU 实际编译结果为准。
3. 完整 EX 保留为上层定义；只在当前任务内部进行常量化简、指令组合和寄存器复用。共享模板或 JIT 不改变任务的 FIFO 位置，不把多个排队任务合并执行。原 EX、程序版本及来源元数据保留用于导出、审查和恢复。
4. 每次 EX 内相同来源引用按该次固定值计算。显式 `self` 与隐式 q 起点均绑定该次 EX 开始时的 q，不读取 EX 内不断变化的累加器。模型状态在任务实际执行时读取，不能在外部输入接纳时或普通任务入队时提前冻结。
5. 代数优化不能删除触发订阅或契约要求的输入检查。旧 profile 保留原 EX 的参数可取得性检查；新 profile 按显式参数和触发契约校验。参数不足等正常结束分支与可恢复故障分开记录，不把失败伪装成任务完成。
6. 结果发布条件基于本次结果与其版本判断；延迟传播不得回读后来变化的状态。重复同值调用保持独立身份；初始化、传输完成和恢复本身不伪造事件。

**方案 N01-2：来源和状态直接表达。**

| 来源类型 | 含义与绑定时机 |
|---|---|
| `CONST` | 布尔常量。 |
| `STATE` | 独立状态槽；任务实际执行时绑定其应读取的版本。 |
| `VALUE` | 某次计算结果的不可变版本；可引用已有前序结果或声明事务内部的暂存结果。 |
| `PARAM` | 当前任务锁存的输入、事件或其他不可变参数。 |

计算来源、状态写入和触发订阅独立描述。触发来源可以不参与算术；任务形成仍须满足该模式的来源和输入要求，不以缺失值 0 代替未到达。无状态节点不因设备分配临时值槽而变成有状态节点。

**CUDA 表示。** 状态、程序、操作数绑定、订阅边及任务描述分别使用设备 SoA 数组。稳定逻辑 ID、世代和程序版本映射到设备槽位；物理搬页不改变逻辑身份。紧凑索引超出范围时切换宽索引或明确报错，禁止截断。模板与编译缓存可共享，每个 FIFO 任务仍持有独立的参数绑定和消费状态。

#### 输入和设备接入

**方案 N02：外部输入先形成输入任务，执行该任务后才可能发布事件。** 同一 `send` 中各端口按声明次序形成独立输入记录和任务；整次输入校验、容量预留和锁存成功后才接纳。每个任务登记队列归属、入队序号及不可变载荷。不同请求的相同 bit 仍是不同输入任务。

```text
外部 send／CUDA tensor
    ↓ 校验、锁存、预留 FIFO 记录
输入任务入 FIFO（accepted）
    ├─ 异步 H2D／设备载荷发布 → device_visible
    └─ 可选持久日志 → durable
    ↓ 当前任务完整结束，调度器选中该输入任务
等待本任务载荷可读 → 执行输入节点／适配程序
    ↓ 提交并判断发布
输入任务的事件入 event_queue → 完成传播和目标任务入队
    ↓
该输入任务结束
```

- 输入任务可执行对应输入复制节点或显式登记的输入适配程序，例如以 `J0K(PARAM)` 表达复制锁存值。是否使用同编号节点由 profile 定义，但不能以省去复制节点为理由省去输入任务、FIFO 调度和传播完成边界。
- CPU 数据、pinned host 内存或 CUDA tensor 只决定数据如何到达设备，不改变任务排队规则。宿主接纳、设备传输就绪和持久确认分别报告 `accepted / device_visible / durable`；传输完成不生成模型事件，也不更新目标触发状态。
- 接纳入口记录逻辑入队次序并短暂持锁，不能在锁内等待 GPU、文件同步或应用回调。异步设备合法性检查结束前返回 pending；检查通过并取得任务与载荷所有权后才声明接纳。
- 参数在消费者结束前不可变。`record_stream` 只保护生命周期，不防止调用者修改 tensor，也不代替跨 stream 依赖；必要时复制到运行时拥有的载荷区。
- 快照仍记录输入接纳水位及已执行输入进度；这些水位用于保存与恢复，不再用于组选择或让外部输入直接参与事件匹配。

### 3.3 第一类：事件传播与任务入队

传播工作者只消费归属当前活动任务的 `event_queue` 记录，沿事件绑定的实际订阅关系展开。不同任务的传播阶段不重叠；当前传播中形成的目标任务只追加 FIFO，不代替目标执行 EX。

```text
当前任务发布事件
├─ 核对 owner_task_id、事件身份、世代、订阅版本和事件内顺序
├─ source_offsets[source] → 取得真实订阅边区间
├─ 并行读取 target_slot / target_input，形成逐边投递
├─ 按规定次序更新目标的输入匹配状态
├─ 每次满足条件 → 独立 TaskDesc → 正式追加对应 FIFO
└─ 全部投递、匹配和入队可见 → 该事件传播完成
```

**方案 N03：由 CUDA 代码维护触发状态和任务形成。**

| 模式 | 设备状态及语义 |
|---|---|
| `ANY` | 每次满足订阅条件的事件形成独立任务，不合并重复值。 |
| `ALL_LATEST` | 每来源记录有效位和值；未齐期间同源新值覆盖，收齐后形成任务并清空本次配对。 |
| `ZIP` | 每来源保留未消费事件的 FIFO，按来源内顺序逐项配对。 |
| `KEYED` | 按业务 key／帧 ID 分桶；同 key、同来源使用 FIFO，按顺序配对。 |

0 是有效值，不能当作未到达；CUDA batch 编号不是业务 key。四种匹配状态及剩余 token 都有明确所有权和容量，独立于当前活动任务的结束判定。

**确定性 CUDA 管线。**

1. 从事件已绑定版本的 CSR 基表及 delta 枚举真实订阅边。计数、前缀和与 scatter 仅处理当前任务的事件／投递；高扇出可由多个 warp／block 分担。逻辑工作量为实际扇出之和，不扫描全模型判断每个目标是否调用。
2. 投递项保存 `(owner_task_id, event_seq, subscription_order, target, source_position, value_ref, key)`。事件顺序来自当前任务的发布契约；同事件的订阅顺序来自显式逻辑顺序，不能由 CSR 搬页位置或线程完成先后重定义。
3. 不同目标的投递可以并行；同一目标有多项投递时，由独占处理者按逻辑顺序更新匹配状态。只有一个活动任务不意味着一个任务绝不会生成多条事件，或一个事件绝不会命中同一目标的多个输入。
4. 每次触发形成独立任务，通过计数、前缀和与稳定写入保留其规定入队次序。可批量追加多条记录，但每条记录的身份、FIFO 位置、载荷和就绪发布都必须完整。外部输入任务的并发追加按 Q01 的逻辑入队入口线性化。
5. 若同一任务的合法发布序列为 `A=0、B=1、A=1、B=0`，`ALL_LATEST` 应形成 `(0,1)` 和 `(1,0)` 两次配对，不能只保留每来源最后值。若这些事件来自不同任务，则依次在各自任务的传播阶段完成同样的匹配。
6. 超过临时容量时可分块续接或补页，保存投递游标和已完成入队范围。不得公开一部分结果后截断；也不得提前执行已生成的目标任务来释放队列容量。
7. 未齐输入存入其匹配器后，本次投递即完成；不等待后续任务送来其他来源。传播完成标记必须晚于所有匹配器写入和目标 FIFO 发布，当前任务才能结束。

**原 R01 的处理：**原“内部后继事件与外部输入直接合并传播”的待确认项撤销。外部输入先执行 FIFO 输入任务，不存在一条绕过任务执行而直接进入传播的外部路径。事件先后由任务选择次序及单任务发布顺序确定；同一 FIFO 的任务追加仍须遵守上述入队线性化规则。

调用描述在入队时固定任务身份、队列归属、程序版本、锁存事件／VALUE 引用和状态来源／目标槽描述，不提前读取 STATE 或冻结 q_seed。程序修改、订阅修改和触发余项的具体版本契约仍须清楚声明；取消并行执行不自动消除所有动态版本问题。

### 3.4 第二类：任务执行与事件入队

任务执行工作者只处理调度器选中的 `active_task`。输入任务、EX 任务、声明的原子事务任务以及业务控制任务均经过 FIFO；不同任务种类不构成绕过队列的执行入口。

```text
领取一个 FIFO 队首，安装 active_task
├─ 核对载荷就绪、身份、程序版本和任务资源
├─ 绑定 PARAM／VALUE／STATE 与 q_seed/self
├─ 执行当前 EX 或声明任务程序，保存候选结果
├─ 校验并提交当前任务的结果／结构效果
├─ 按发布契约生成本任务事件，写入 event_queue
├─ 交给传播阶段，保持当前任务为 ACTIVE
└─ 所有传播、目标匹配和新任务入队完成后，发布 COMPLETE
```

**方案 N04：一个活动任务，完整执行后重新选择 FIFO。**

1. 即使两个排队任务没有数据依赖，也不能同时执行。相同状态槽的读写自然服从任务执行先后；后面的任务只有在前面任务完整结束并被正式选择后，才绑定自己应读的状态。
2. 显式 `VALUE` 可引用已有不可变结果。模型不得让已经占住活动位置的任务等待只能由后续 FIFO 任务产生的结果；输入配齐／任务就绪规则应在任务形成前保证合法，或按相应 profile 明确拒绝／正常结束。
3. 已声明的原子事务可以有自身的有序内部操作及 EX；它作为一个 FIFO 任务领取并遵守独立提交契约。内部操作逐项按依赖和声明顺序推进，不并发执行多个独立调用。原本独立的任务不能因被标为“事务内部”而免于 FIFO 或省去传播完成边界。
4. 普通任务内部参数读取和长 EX 的保序组合可由多个线程协作，单比特短 EX 可由一个线程在寄存器中执行。J/K 变换的组合不可交换，归约必须保持原 EX 次序，尾部填充采用恒等变换；算术并行不消除动态来源的 gather 成本。共享程序、预编译和 JIT 都只服务当前选中任务；未命中 JIT 时由通用解释器覆盖合法 EX。
5. 提交后生成的事件必须持有不可变结果及订阅版本。当前任务在事件入队后继续保留活动身份，直到传播完成；不以“已经通知传播者”代替完成。
6. 不发布事件的任务，在其声明的执行／提交义务完成后结束。参数不足等契约定义的正常结束，与等待、失败和提交后交接续接分别表示，不能通过标记失败为完成跳过 FIFO。

以下仅示意一个已选中短 EX 的设备求值；`seed` 与 `inputs` 已完成该次绑定及 0/1 校验。它只写本次结果，提交、事件生成和传播由运行时继续推进，尚未编译或测量：

```cpp
__global__ void eval_current_task(
    const uint8_t* seed, const uint8_t* inputs,
    const uint8_t* op_kind, const int32_t* op_arg,
    int32_t op_count, uint8_t* result) {
    if (blockIdx.x != 0 || threadIdx.x != 0) return;
    uint32_t q = *seed;
    for (int32_t t = 0; t < op_count; ++t) {
        uint32_t x = inputs[op_arg[t]];
        q = (op_kind[t] == 0) ? (q & x) : (q ^ x); // J=0，K=1
    }
    *result = (uint8_t)q;
}
```

一个 kernel 可以包含多项内部操作，常驻 kernel 也可顺序完成多个任务，但每个任务之间必须真实经过“传播完成 → 本任务结束 → 重新选择 FIFO”。不得预先领取多个任务后连续执行，以免跳过传播中新入队任务应参与的队列选择。

### 3.5 两个逻辑队列与交接协议

**方案 Q02：任务 FIFO 与当前任务的传播队列。** 两类队列都用设备数组或分段页池保存记录。`task_queue` 表示按 profile 定义的一个或多个任务 FIFO；`event_queue` 保存当前活动任务的传播工作。事件队列不是另一条可独立选择模型任务的入口。

| 队列 | 生产者 → 消费者 | 记录内容 | 可消费条件 |
|---|---|---|---|
| `task_queue` | 输入／控制接入及当前传播 → 任务调度器 | task_id、类型、FIFO 归属、入队序、程序版本、锁存载荷、状态槽描述和生命周期 | 当前没有未完成活动任务；按队列策略选中队首；记录与所需载荷可读。 |
| `event_queue` | 当前任务的提交／发布阶段 → 传播工作者 | owner_task_id、event_id、来源／世代、订阅版本、发布序、不可变值／key、扇出游标 | 记录已发布、所需提交可见，且属于当前 active_task。 |

**方案 Q03：预留、写入、发布、消费和回收分开。**

1. 生产者先预留容量，再写完整记录及载荷引用，最后发布可消费状态。单独 `atomicAdd(tail)` 不能证明记录已经写完；逻辑入队次序不由各投递线程抢到的物理槽号产生。
2. 并发生产／消费用明确作用域的 release/acquire；同一 stream 的分阶段 kernel 可用 stream 顺序，跨 stream 用 CUDA event 建立依赖。`__syncthreads()` 不同步整个 grid；多个线程协作写一条记录时，发布前必须汇合全部写入。
3. 环形槽使用序号／世代和独立就绪状态防止读到旧轮数据。消费者持有期间不得回收载荷；取消未公开预留、失败续接和正常完成分别释放信用，不能留下永久阻塞的空洞。
4. FIFO 追加由逻辑入队协调器维护，实际记录可批量 scatter。入队序一旦登记，不能因后项更早上传完成而越过前项；快照和日志保留逻辑次序，不依赖物理地址。
5. 事件完成计数必须包含尚未生成完的事件、队中事件、已领取未完成投递以及尚未发布完的目标任务。生产阶段封口后，所有计数与持有者归零且写入可见，才能结束当前任务；瞬时队列空不能单独作结束条件。
6. 队列满时保存当前任务和传播游标，补页、背压或报告资源等待。不能通过提前执行队尾任务释放空间，也不能让两个角色持有计算资源无限互等。管理路径须可补充容量或保存现场，不依赖后续模型任务先运行。
7. 事件载荷与相关订阅／程序版本保留到全部投递完成；目标任务再按自己的引用生命周期持有已锁存参数。当前任务完成不强行释放已转交后续任务的值。

### 3.6 CUDA 工作映射、stream、内存与前进性

**方案 N05：PyTorch tensor 管理设备数组，C++/CUDA 扩展实现单活动任务状态机。**

| 物理执行方式 | CUDA 映射 | 必须保持的任务边界 |
|---|---|---|
| 有界分阶段 kernel | 当前任务绑定／EX／提交后，运行其传播／匹配／入队 kernel | 传播完成后再启动或选择下一任务；一次传播可批量处理很多边。 |
| 有界常驻工作者 | 同一 kernel 中由协调者持有 active_task，线程／warp／block 按当前阶段协作 | 设备内完成任务判定并重新选择 FIFO，不依靠 CPU 逐事件通知；预算耗尽或等资源时保存现场让出。 |

两者都是实现选择，需要实测。分阶段实现的启动成本计入端到端耗时；常驻实现不能假定两个独立 kernel 会公平并发。两类角色不固定各占一半 GPU，也不在上一任务传播时提前执行下一任务。

- 使用 device/stream guard；输入准备、当前任务计算、输出复制和快照复制可使用独立 stream，但任务执行与事件传播由显式状态和依赖约束。`cudaEvent_t` 标记 CUDA stream 工作完成，不提供 JK 订阅、触发或任务队列。
- 固定容量 CUDA Graph 可承载已经明确的当前任务阶段及传播片段；设备 count、valid 位和工作区用于动态负载。不能把“按模板预发多个 EX 任务”作为图捕获优化。CUB 接口的 `num_items` 等宿主参数不能未经核实就替换为设备指针。
- 常驻工作者等待无法取得的资源时必须有界退出，保存当前任务和传播进度；不得在它仍未完成时选择另一个任务。不能仅靠预留 SM 或 stream 优先级证明前进性。
- NVRTC 模块不会自动内联进已编译常驻 kernel。热点程序可以在当前任务的安全阶段选择专用 kernel，或切换完整 dispatch；模块、graph 和 tensor 保留至最后使用结束。缓存键包含程序、ABI、编译器、GPU 架构和布局。
- 单任务内部的 bit 打包写入仍可能出现不同 bit 共用一个字的读改写冲突；采用整字独占、合并掩码或适当原子操作。只读载荷和合法的任务内部位运算可使用位切片，不能以打包为理由合并独立 FIFO 任务。
- 状态、边、任务、事件和输出使用分段池，宿主可补页；物理搬移和扩容不改变身份和 FIFO 次序。输出复制或快照读旧页可以与当前任务协作，但不得让后台线程直接修改模型触发状态。
- 校验失败、容量不足、异步 CUDA 错误和致命故障分别报告。正常数据拒绝不使用会污染上下文的 device assert；非法访存或设备丢失不按普通 OOM 原地重试。

**验收关注。** 对同一逻辑入队／选择记录，改变 block 大小、传播分块、stream 延迟及 allocator 复用，核对状态、匹配、队列和输出轨迹。重点验证事件已入队但传播未完、传播线程仍持有投递、目标任务写入尚未发布时，下一任务均不能开始。实际编译、Compute Sanitizer 和 GPU 性能仍待验证。

## 4. 更快运行两个任务队列

**目标与边界。** 提高当前任务的传播、EX 和交接速度，降低完整 FIFO 循环耗时。保留两类工作、两类队列及每个任务和事件的完整身份；只优化任务内部和本次传播，不增加跨任务同时执行。短 EX 本身可能只需少量位操作，应测量调度、内存访问和传播成本，不能以 GPU 利用率为由改变任务边界。

```text
更快运行两个任务队列
├─ PERF-P：传播阶段的处理速度
│  └─ 当前任务的订阅读取 → 扇出展开 → 输入匹配 → 新任务入 FIFO
├─ PERF-X：EX 阶段的处理速度
│  └─ 当前队首的参数／状态读取 → EX → 提交 → 生成事件
└─ PERF-H：两个阶段之间的交接速度
   ├─ 队列预留、记录写入、发布、领取和回收
   ├─ 当前任务阶段切换及传播完成判定
   └─ 本任务完整结束后，设备重新选择下一个 FIFO 队首
```

### PERF-P　传播阶段的处理速度

| 编号 | CUDA 实现方案 | 必须保留的语义与测量重点 |
|---|---|---|
| PERF-P01 | 来源按设备槽定位 CSR 与已提交 delta，相邻订阅边连续存储。 | 只展开真实订阅；计入索引、delta 和目标访问成本，保留绑定订阅版本。 |
| PERF-P02 | 对当前任务事件的扇出计数、scan 和分块，高扇出由多个 warp／block 处理。 | 不把不同 FIFO 任务的事件混成并行传播；每次投递身份及逻辑次序不变。 |
| PERF-P03 | 不同目标并行，同目标多投递由独占处理者依序匹配；需要时稳定分组。 | 保留四种触发模式和全部配对次数；传播未齐只保存 token，不阻塞等待未来任务。 |
| PERF-P04 | 当前传播形成的任务批量预留、填写并追加对应 FIFO，恢复规定的目标入队次序。 | 新任务只排队；完成发布后才能计入本次传播已完成，不能顺手调用其 EX。 |

| PERF-H06 | 预留事件、目标任务和续接空间；容量不足时保存当前活动任务、补页或等待资源。 | 不能靠执行后续 FIFO 任务释放空间；完整统计未领取、已领取、未发布目标任务及生产封口状态，再判断本任务结束。 |

## 5. 事务、动态结构、帧存储与环监督

本节统一遵守逐任务 FIFO 边界：一个实例同一时刻只有一个活动逻辑任务；当前任务完成计算、提交、全部规定事件的传播及目标任务入队后，才结束并重新选择任务。输入、ACK、输出完成控制和外部结构修改请求都先形成有身份的任务并进入对应 FIFO。物理页、CUDA stream 和线程只承载实现，不产生新的业务顺序。以下均为设计，代码、GPU 运行及性能尚未验证。

### 事务与动态结构总览

```text
已登记的事务任务进入 FIFO
    ↓ 按队列选择规则轮到该任务
唯一活动任务
├─ 绑定 TxDesc：事务 ID、契约和程序版本、输入及状态版本、操作清单
├─ 按已声明顺序执行事务内部步骤
│  ├─ 外部参数和目标身份：实际可取得后使用
│  └─ 前序内部结果：以暂存 result/version 供后续步骤使用
├─ 预估并预留候选页、后继任务、事件、输出及临时工作区
├─ bind → evaluate → 产生候选写集
├─ 校验版本、合并本任务写集、安装候选版本根
├─ 按声明顺序发布并完成全部规定事件的传播
├─ 传播满足条件的目标任务分别进入 FIFO
└─ 本任务完成 → 重新选择 FIFO 队首任务
```

#### T01　事务描述、内部步骤和逻辑提交

- **任务边界：**只有模型契约原本声明为一个 FIFO 原子任务的事务，才可在该任务内完成其内部步骤；每个事务及内部 EX 保留稳定身份和明确执行次序。不得把原本独立的任务重新归为事务内部操作，以绕过 FIFO、其传播边界或入队记录。事务内部前后结果依赖不改变其他任务必须排队的要求。
- **设备数据：**`tx_desc[]`、读写目标与版本、`planned_creations[]`、结构增删、内部 EX 序号、结果引用、资源清单、发布意图及状态标记采用分段设备数组。地址只用于定位，不替代任务或事务身份。
- **输入与结果：**事件锁存参数和状态槽版本分别记录。事务外提供的参数及对象身份在使用前必须实际可用；已声明的内部后序 EX 可以读取前序 EX 的暂存结果，使用显式 `result_ref`，不能把尚未产生的结果视为可读参数。由事件触发的其他节点任务只入 FIFO，不能在当前事务中临时直接调用。
- **q 起点和自引用：**每次 EX 开始时的隐式旧 q 和显式 `self` 读取同一个固定起点，不指向中途变化的寄存器累加器。相同状态槽及别名按当前任务内的声明次序访问；不同 FIFO 任务之间按实际选择和完成次序访问。
- **提交与可见性：**各事务串行取得活动任务身份，不能并行准备业务状态、计算或提交。每个事务有独立提交记录；条件失败、回滚、已提交和传播未完成分别记录。允许优化当前任务内部的页复制、索引处理和不改变语义的物理操作，不允许合并独立任务的逻辑提交。
- **stream 依赖：**上传完成 event 约束当前任务读取；当前任务所用计算 stream 的完成 event 汇入提交 stream；根安装完成 event 约束本任务后续传播及输出准备。`cudaEvent` 只证明其关联依赖完成，Python 返回或无关联 stream 的完成不能代替此判断。不同 stream 不授权下一个 FIFO 任务提前执行。
- **失败与续接：**提交前失败释放未安装候选并保留当前任务及已绑定参数；提交后不重算，继续保存的传播和交接进度。当前任务失败或资源等待期间仍持有活动任务身份，其他任务留在 FIFO，不因“独立”而越过。正常传播全部完成后才释放活动任务身份。
- **验收：**串接事务、同状态槽别名、已声明的内部多 EX 依赖和多次同目标调用按既定版本求值；当前任务中途失败时，后续 FIFO 任务不执行；重试不重复提交或传播，准备失败不公开部分结构。标注：_______。

#### T02　候选页与版本根

- 根描述符引用状态页表、节点／EX／连接版本、触发集合、任务及输出等逻辑现场。输入接纳和 FIFO 追加记录独立管理；安装当前任务的候选根不得覆盖运行期间新接纳但尚未执行的输入任务。
- 当前任务修改页时使用候选页和分层页表；读者持有已绑定版本。校验后按该任务的提交次序发布根索引／版本；跨 kernel 使用 stream 次序或 event，确有并发读者的访问使用明确作用域的发布／读取同步。
- **连续任务不丢写：**若原页含 `A=0,B=0`，前一个任务写 A 并完成，后一个任务写 B 时必须基于前一任务已提交的状态构造候选，不能安装陈旧整页覆盖 A。同一任务内多个合法写入按声明次序合并 dirty patch；后台快照保存的旧页也不能覆盖新的运行根。
- 提交前完整预留本任务的写集、事件、输出及后继登记所需容量；大扇出可使用已有容量归属的分段续接空间，不能只保存游标而没有空间承接后续义务。准备时容量不足保持未提交状态；提交后发生故障或传播尚未完成时，保留当前任务及其进度，不回滚或重算已提交部分。不能公开半提交，也不能把“事件已入队”当成“传播已经完成”。
- **验收：**连续两个任务写同页不同槽均保留结果；同槽写入依 FIFO 任务次序生效；快照复制、输入追加和 stream 延迟不造成旧根覆盖；容量不足时后续任务不能提前开始。标注：_______。

#### T03　节点、边、版本与生命周期

```text
结构修改请求 → 修改任务进入 FIFO → 轮到该任务后执行
    ↓
逻辑身份：Node ID + generation + program version
    ↓ 映射
设备槽位／状态槽／程序模板／连接表页
    ├─ 计算来源索引与触发订阅索引分开
    ├─ 稀疏 CSR 基表 + 已提交增删 delta + 存活信息
    └─ 候选版本校验并安装；旧版本等待持有者释放
```

- GPU SoA 分别保存节点、状态、程序、操作数、订阅边、事件与版本映射。外部改图／改 EX 请求只登记任务和不可变请求内容，不能在接入路径直接改动模型。由当前任务契约明确规定的结构操作属于该任务，其来源和次序必须可追溯。
- 当前任务的传播结束后，结构修改任务才可能获得执行机会；因此不会在前一任务的传播中途切换订阅表。已排队任务仍保留其绑定版本；新连接表由修改任务的 kernel 在候选缓冲区构建，物理搬页和 CSR 重建不改变逻辑身份。
- 改 EX 安装新的不可变程序版本；解释器覆盖合法程序，热点缓存按程序 ABI、模板、设备架构和版本切换。已入队的旧任务继续其绑定版本；旧代码模块和数组等最后一次使用完成后回收。修改本身不伪造业务事件。
- 修改订阅或触发契约时，已经留在 `ALL_LATEST / ZIP / KEYED` 等待区中的输入仍有身份和所有权；具体版本继承或迁移必须由模块契约明确，不能因为任务执行改为串行就隐式清空、混配或丢弃。FIFO 消除了当前传播与修改同时执行的问题，不自动补足此项契约。
- 删除分为逻辑退休和物理回收。保护范围包括排队任务、当前任务、锁存输入、状态读版本、输出载荷、事务暂存及快照；静默节点同样检查真实引用。旧任务和旧事件不转投不属于其绑定版本的新对象。
- 块或槽复用先解除全部持有，再推进 generation；旧任务、旧帧、旧 ACK 不得命中新对象。逻辑编号可有空洞；设备索引宽度按容量校验，不截断身份或允许世代回绕。
- **验收：**改图请求在当前传播期间到达时只入队；轮到修改任务前旧传播完整结束。检查旧程序任务与新版本共存、未齐输入的明确迁移规则、删除高编号后再创建及帧槽复用。标注：_______。

### 异步帧、输出与 ACK

#### S01　参数化帧存储与计算接入

```text
输入帧（Frame ID、W、位序、接纳序号、不可变载荷）
  → 形成输入任务并进入 FIFO
  → 轮到输入任务：读取载荷、执行输入处理并传播
  → 触发的存储／业务计算任务进入 FIFO
  → 各任务依次执行、提交并完成自身传播
  → 输出记录与后续完成控制任务
```

- 新模块按配置支持帧宽 `W` 和块容量 `K`，同时预留数据槽和元数据显存；宽度超过机器字时使用多字或分段表示，物理页大小不等于业务块容量。输入帧保留实际 W、帧身份、位序和独立载荷，不能从最新输入重拼旧帧。
- 旧模块 profile 保留 W=1–8 和每块每世代八个接纳槽；满八、全部消费且依赖解除后才允许整体释放／复用。新模块的容量及复用范围由契约确定，槽级复用必须有槽世代。
- 领取、队首推进、到达和就绪可由当前任务的 CUDA 控制数组与 kernel 实现；业务计算仍来自约定的节点 EX／计算块。输入搬运、缓存更新和元数据准备不能代替输入任务执行，不能在输入任务获得执行机会前触发下游。
- 保持历史帧含义时按宽度保存 `S_W/C_W`，不能把全部宽度悄悄共享一份 C。零值、相同 parity 和重复帧均按独立事件和帧身份处理，不按计算值去重。
- 声明式业务 DAG 列出输入输出、跨轮状态、依赖及各 FIFO 任务边界。PRE／领取／计算／提交／POST 按其声明的任务或任务内步骤执行。多帧可以排队并持有各自载荷，不授权多个帧任务同时执行；共享状态按任务次序读取和写入。
- **验收：**W=1、8、超过 8，部分使用块、满块增长与合法复用、重复 0 和相同 parity、不同宽度交替输入均保持载荷和世代正确；旧 profile 满八条件不被新 K 覆盖；输入任务未执行时不发生模型传播。标注：_______。

#### S02　输出批次、完成标记和外部交接

- 每个输出批次锁存后拥有自身 frame ID、帧世代、实际宽度、数据位和 marker 载荷；旧数据槽释放或后续帧到达不能改变它。
- 输出任务先进入 FIFO，轮到后执行其节点 EX／计算块并形成不可变输出记录；逻辑序由实际 FIFO 任务执行次序和任务内发布次序确定，不用线程完成或原子抢位顺序。发布条件依据该次调用结果及版本判断。
- 路径为设备记录 → 等待关联计算／提交 event → D2H → 宿主 outbox 接管 → 应用处理。模型内传播完成和稳定输出记录登记归属于当前任务；宿主接收与应用回调通过独立 I/O 路径完成，不在回调中继续执行该任务或直接修改模型。模块明确要求在本任务内完成的交接仍须满足，不能以“已登记输出”代替其规定的完成条件。
- V6.1 新 profile 的 `FRAME_OUT` 外部交接点仍是宿主接收完成：该帧实际 W 个数据记录先交接，随后 marker 完成交接。宿主形成携带 frame ID、世代和 output_id 的完成控制任务并进入 FIFO；只有轮到该任务执行，模型资格才按契约更新。旧 V5 的完成与资格边界仍依其对应契约。
- 宿主将 marker 交给应用前，先确保完成控制任务已被可靠接纳并取得 FIFO 位置；预留控制容量防止普通输入占满接入空间。控制任务不能插入当前任务的传播；当前任务也不等待未来的控制任务或业务 ACK 执行后才结束。宿主接收、控制任务执行和业务 ACK 是三个独立事实。
- 新输出接口允许带 frame ID 和帧内位置的记录跨帧交错，但实际交接仍受任务产生的逻辑序及同帧 marker 依赖约束；旧无帧 ID 接口按帧连续输出。此能力不表示多帧任务并行执行。
- **验收：**W 项完成前不能宣称 marker 交接完成；完成控制记录排队期间不得提前建立资格；回调再次 `send` 不死锁；复制完成先后不改变逻辑输出顺序。标注：_______。

#### S03　ACK 译码、资格与动作

- ACK 先作为有独立 ID、锁存值和接纳次序的输入任务进入 FIFO，不在宿主接入时直接译码或消费帧。DEC 任务轮到执行时读取当时队首、frame ID、槽／帧世代和资格；成功后按模块契约形成携带 `FrameRef + generation + qualification_token` 的 ACT 任务并入 FIFO。
- ACT 轮到执行时核对先前绑定的对象；已消费、已重用或资格不匹配时无业务效果，不重新选择下一帧。真实状态变化和队首推进在其声明的事务边界提交。若契约原本将译码与动作定义为同一个原子任务内步骤，保留该既有边界；不能由优化临时合并两个独立任务。
- 资格零是有效值。DEC 看到资格为零时按契约无动作，不挂起当前任务等待未来完成控制；两个 ACT 绑定同一帧时，第一个消费后第二个不得转而消费后继帧。旧重发或迟到 FRAME_OUT 完成不得复活已消费资格。
- ACK 到达时间和 DEC 执行时间分别记录。只有在 DEC 执行之前，相应完成控制任务已经按 FIFO 规则执行并建立资格，ACK 才可能生效；物理接收时间不能替代任务顺序或资格判断。
- ACK0／ACK1 的业务含义、首发与重发、数据保留和资格撤销依模块契约；输出接收确认不冒充业务 ACK。多个在途帧分别保存资格，不用一份全局奇偶标志代替。
- **验收：**无资格的 DEC 正常结束；控制任务已执行后再轮到 DEC 时按资格判断；两个 ACT 绑定同帧只消费一次；旧动作不命中新世代；所有这些任务都经过 FIFO，没有接入旁路。标注：_______。

### 环、监督与动态回收

#### L01　环的识别和运行预算

```text
建图或轮到结构修改任务提交
├─ 计算数据版本依赖图：检查可启动的初值／延迟边
└─ 计算触发订阅图的 SCC：记录身份、成员、调用预算和状态
   ├─ FIFO 任务轮到执行前检查适用预算
   ├─ 执行当前任务，完成提交和传播，计入逻辑调用数
   ├─ 达到边界：保留排队任务、输入和监督状态
   └─ 明确恢复：沿保存的 FIFO 现场继续
```

- 允许事件反馈环。结构任务提交后检查受影响子图；订阅图的环与计算／版本依赖环分别判断。没有初始令牌、初值或延迟边而无法启动的数据环，必须有明确启动规则，否则加载或修改失败；预算本身不能产生所缺参数。
- 预算按实际逻辑调用计数，不能按 kernel 启动数计数；已声明原子事务中的内部 EX 也按其契约记账。任务开始前检查适用预算及原子边界，不能在预算到达时把尚未完成传播的当前任务宣告完成。达到预算保存剩余任务、未齐输入和暂停状态。
- 暂停不自动清除任务、载荷或历史计数。暂停或资源等待中的当前任务没有完成时，不选择另一个任务。同一 FIFO 不得越过受阻队首；若运行契约包含多个 FIFO，只能在完整任务边界按既有队列选择规则处理其他队列，不能因“另一个 SCC 独立”就擅自跳过队内顺序。
- 显式恢复继续原现场并按配置进入后续预算段；快照恢复不隐式重置预算和暂停原因。运行监督器的暂停／恢复或补页是在维护已有任务进度，不得通过它直接执行业务 EX 或绕过 FIFO 产生模型事件。
- SCC 合并或拆分时，候选结构、未齐输入、排队任务、历史预算与暂停状态一并检查；具体继承映射写入模块契约。此规则仍需具体化，串行执行不自动决定如何分配预算，物理槽变化不能把活动环当作新历史。
- **验收：**状态反馈、无初值数据环、预算边界、暂停时新输入任务到达、SCC 合并拆分及恢复均保留正确身份和 FIFO 次序；持续无输出不自动判为死环。标注：_______。

## 6. 输入、输出与宿主交接

```text
外部输入提交
├─ 校验身份和值、预留容量、取得不可变载荷
├─ 形成输入任务并登记到 FIFO → accepted
├─ H2D／设备到设备传输 → device_visible（仅表示数据准备好）
├─ 可选日志同步 → durable
└─ 轮到输入任务 → 读取载荷并执行 → 按契约产生事件并完成传播

模型输出
├─ FIFO 中的输出任务轮到执行
├─ 当前任务提交、完成规定传播并登记稳定输出记录
├─ I/O 路径复制到宿主 → 宿主接收完成
├─ 必要的完成控制任务进入 FIFO → 轮到后更新模型
└─ 应用读取／回调；业务 ACK 作为新的输入任务排队
```

### 输入协议

- [ ] **接纳边界。** 每次提交有独立 input_id、端口和值、来源身份；整次校验、容量预留、不可变载荷取得及输入任务 FIFO 位置登记成功后，才确认 `accepted`。多端口输入按契约固定次序登记输入任务，不能只复制最新值。0 和重复值均保留独立输入身份。接纳和搬运不执行输入任务，不直接触发模型事件。
- [ ] **三个确认点。** `accepted` 表示任务和载荷已可靠接纳；`device_visible` 表示所需设备记录及载荷可读；`durable` 表示约定持久日志已同步。三者均不表示输入任务已执行或传播完成。后两者可以先后独立完成；GPU tensor 异步校验未结束时 ticket 保持 pending，校验失败返回 rejected。
- [ ] **FIFO 与 CUDA 同步。** 已接纳输入任务的逻辑位置不由 H2D 完成先后决定。轮到某输入任务而其载荷尚未可读时，保存该任务的等待状态并等待对应 event／发布握手；不能越过它执行同一 FIFO 的后续任务。当前任务执行期间的新输入只追加任务和准备载荷，不插入正在进行的 EX 或传播。
- [ ] **追加顺序。** 外部接入和当前传播可能同时向同一个 FIFO 追加任务；统一的入队线性化机制给每项任务确定并记录逻辑位置，恢复沿用该记录。并发追加不表示并发执行或并发传播，也不按“内部／外部”来源擅自设立新的优先规则。
- [ ] **所有权。** pinned 缓冲区保持到 H2D 完成；设备载荷保持到全部消费者释放。输入为 CUDA tensor 时，执行器等待生产者 current stream 的事件，并持有引用或调用 `record_stream` 保护分配生命周期；仍须复制或明确接管不可变数据。直接使用设备载荷不等于直接形成模型事件。
- [ ] **容量与配对。** 接纳前预留输入任务、载荷及必要元数据；必要时拒绝或背压，不能部分接纳。传播到目标后未收齐的 `ALL_LATEST / ZIP / KEYED` 输入保留在等待区；本次投递和匹配已经完成，无须等未来来源到达才结束当前任务。真实容量耗尽时保存当前任务现场，补页、等待资源或报告资源故障，不丢已接纳记录，也不提前执行后续任务来释放队列空间。

### 输出协议

- [ ] **设备到宿主。** 输出记录按实际任务执行次序及任务内发布次序编号；egress stream 等关联提交 event 后复制。宿主 D2H 成功并取得独立不可变载荷才算外部交接；设备根标记、输出入队或 Python 返回都不能代替宿主接收。
- [ ] **解耦回调。** drain 路径将设备输出转交宿主 outbox，应用回调在独立路径执行，不持有模型提交、接入或接收锁。回调中的 `send` 只登记新的 FIFO 输入任务。回调失败重投原 output_id，不重跑 EX；I/O 线程不得直接触发模型或修改资格。
- [ ] **帧输出与控制任务。** 新接口允许按既定逻辑序交接带帧 ID 和位置的记录；同帧 W 项完成后才能形成 FRAME_OUT 完成事实。宿主将完成事实转换为有身份的 FIFO 控制任务，轮到执行后才更新资格；业务 ACK 另行排队。当前任务不等待未来的控制任务或 ACK 完成，避免当前任务占住执行位置而阻止所等待的任务运行。
- [ ] **值与条件。** 结果、发布条件和锁存输出载荷属于原任务版本；延后交接不回读最新 q。重复同值输出保留身份；不发布或正常无动作按契约终止当前任务，不留下永远未完成的记录。任务完成账本与异步外部交接账本分别记录。

## 7. 失败、重试与资源管理

```text
唯一活动任务
├─ 资源不足 → 保存当前阶段和游标 → 补页／背压／明确资源等待
├─ 提交前可恢复故障 → 保留身份及固定参数 → 显式 retry
├─ 提交后传播故障 → 保留提交及传播进度 → 续接未完成投递和入队
├─ 所有规定工作完成 → 本任务结束 → 重新选择 FIFO 任务
└─ CUDA 致命故障 → 停止执行域 → 重建上下文／进程 → 恢复可信现场
```

- [ ] **故障分类。** 正常无动作、条件不发布和陈旧 ACK 与故障分开；缺页、可恢复错误、非法访存／device assert／设备丢失分别报告。检查 launch 返回、关联 stream 的 event 和异步 CUDA 错误；正常输入拒绝使用诊断记录，不用污染上下文的 device assert。event not-ready 是等待状态。
- [ ] **预留与提交。** prepare 阶段预留写集、结构变更、事件、后继任务、输出和候选页，以及必要的续接空间。未安装候选可以释放，已提交结果不能回滚成未执行；追加输入区独立于事务根。提交成功后若传播尚未完成，当前任务仍未完成。
- [ ] **双队列背压与续接。** 分别记录 event_queue、FIFO task_queue 和触发等待区的容量、预留、已发布及已领取数量。传播工作者只推进当前任务所属事件及投递；容量不足时保存扇出游标和已入队范围，有界退出 kernel，但保留活动任务身份。补页或 I/O 排空可以释放资源，不能通过提前执行下一个 FIFO 任务解除拥塞。若既无可补容量又无合法排空路径，明确报告资源故障，不能无限自旋或丢弃记录。
- [ ] **当前任务账本。** 记录未开始、参数已绑定、计算完成、已提交、传播中、失败保留、资源等待及完成。当前任务完成的证据包括所有应发布事件已完成规定投递、目标匹配完成、应形成的后继任务已真实入 FIFO；event_queue 暂时为空或 EX 返回都不足以单独证明完成。事件未发布空洞和并行投递尚未收尾也必须计入。
- [ ] **显式重试。** 保留同一任务、帧身份、程序版本、已锁存输入及实际绑定的 q_seed、资源和输出身份。重试续接当前任务，不重新排到队尾；提交前可用固定参数重算，提交后仅续接未完成传播及交接，禁止重复提交、投递或入队。后续任务在当前任务正常完成之前不执行。
- [ ] **宿主与维护操作。** 当前任务等待或失败时，宿主可在容量允许范围内继续接纳输入任务、搬运载荷、排空既有输出及保存现场；这些维护动作不执行后续模型任务。补页、显式重试和故障恢复必须能推进已有任务，不作为排在其后的新业务任务造成自等待。
- [ ] **致命故障。** CUDA 上下文失效后不能读取旧显存或根据残留完成位推断成功；监督器重建进程或执行域，仅以故障前确认的检查点、持久日志和当前任务进度恢复。无法证明的工作按记录重放或报告缺口。普通内存模式不承诺进程崩溃后无损。

## 8. 快照、持久日志与恢复

### 一致快照

```text
请求普通快照
├─ 等待当前任务完成计算、提交和全部规定传播
├─ 暂停选择下一任务，固定 FIFO 现场和输入接纳切点 F
├─ GPU pin 逻辑根、页面及仍被持有的版本
├─ 保存已完成任务位置，以及 accepted ≤ F 的全部未执行输入任务和载荷
├─ 快照 stream 等关联 event，复制受保护页面
├─ 可恢复后续 FIFO 执行；后续写入采用 COW
└─ 写临时文件 → 校验／同步 → 原子发布清单 → 同步目录
```

- [ ] **普通与故障边界。** 普通快照在完整任务边界固定，不能把“EX 已完成但传播未结束”冒充完整边界。当前任务失败或资源等待而需要立即保存时，使用明确的活动任务恢复格式，记录其阶段和部分传播现场，不伪装成普通完成快照。
- [ ] **完整现场。** 保存逻辑结构和初值、状态与程序版本、连接及订阅、FIFO 队列和任务顺序、当前任务（若格式允许）、参数绑定、事务内部结果与创建描述、触发未齐输入、槽／块世代和分配高水位、帧／资格、输出游标及 outbox、SCC 预算、已完成任务位置和输入输出身份。设备指针、stream/event 及可重建物理索引不作为逻辑身份序列化。
- [ ] **两队列恢复。** 保存 task_queue 的完整 FIFO 记录，以及 event_queue 中属于活动任务的未完成事件、消费范围、部分扇出、目标匹配和后继入队进度。普通完成边界不存在前一任务遗留的未完成传播；故障格式则必须保存唯一活动任务与这些事件的归属。恢复先续接该任务，不能先取后续 FIFO 任务。未发布物理预留按账本重建拥有权或撤销，不能当完整事件重复发布。
- [ ] **输入切点。** `accepted_frontier=F` 用于快照和日志的一致切点，不再用于封存并行执行组。保存 F 以内所有未执行或未完成输入任务，包括仍在 pinned 区或 H2D 中的不可变载荷。传输就绪与输入任务实际执行分别记录；可能非连续完成时同时保存各 input_id 的状态，不能仅用最高编号推断之前全部完成。F 之后的接纳不混入本快照。
- [ ] **页面保护。** 协调器在发布快照 ticket 前 pin 根及可达页面；快照 stream 等根和任务边界完成 event。后续任务写入使用 COW，旧页保留到全部读者和快照 D2H 结束。不能先取根、稍后才保护页面；分批复制始终读取同一冻结版本。
- [ ] **保存格式。** 普通格式记录完整任务边界；活动任务故障格式增加未提交候选、已固定参数、已提交状态、事件及后继入队进度。校验并同步临时数据和清单后原子发布，再同步目录；只有确认检查点覆盖对应日志前沿后才能截断 WAL。

### 持久记录与恢复

- [ ] **持久输入。** 耐久模式记录请求身份、输入载荷、接纳顺序、FIFO 位置及输入任务状态；按承诺同步后才确认 `durable`。落盘后回复前崩溃时，以稳定 request_id 查询或重试，同一 ID 不重复接纳，不同 ID 的相同值仍是独立任务。日志记录任务执行与传播进度，不把传输完成记录当作业务执行记录。
- [ ] **提交与输出。** 对已确认 CUDA 完成的提交保存可重建状态、结构、触发状态、后继入队、输出意图及当前任务进度的日志。任务传播全部完成后另记任务完成位置；仅有状态提交日志不能证明任务已经结束。依赖此前提交的结果不得越过未持久的因果前缀。耐久输出先取得宿主私有载荷，再同步关联提交／outbox 记录，最后对外交接；需要恢复重投的未确认输出仍使用原 output_id，不为已确认交接另造输出。
- [ ] **宿主配合。** 外部副作用实现跨进程恰好一次，需要接收方按 output_id 去重或提供幂等协议；运行时不能单独保证任意回调恰好一次。输出完成控制任务、业务 ACK 和传输接收确认分别记录，恢复不重复形成控制任务或提前建立资格。
- [ ] **隔离恢复。** 先校验格式、指纹、结构、FIFO 次序、当前任务、触发和载荷所有权，再重建设备数组、页表和容量信用；成功后以暂停状态安装。普通恢复不自动执行任务或补造事件；故障恢复按当前任务的既有提交和传播游标续接。缺失合法检查点、日志或必要字段时明确报告缺口，不猜测修复。

## 9. 接口、兼容与验收

### 运行接口

- [ ] `from_structure`、`restore_runtime` 创建新实例或隔离恢复；`send` 接纳不可变输入并登记输入任务后返回身份及异步 ticket，分别查询 `accepted / device_visible / durable`。接纳和传输准备不执行输入任务，也不直接产生模型事件。
- [ ] `run`、`pause`、`step` 以**完整 FIFO 任务**为控制单位。每实例只有一个活动任务；`step` 选择并推进一个任务，必须完成其执行、提交、应有事件传播和目标任务入队，才能报告完成。无发布或正常无动作按契约结束；资源等待或可恢复故障保留同一活动任务，不执行后续任务。
- [ ] `run(max_tasks)` 限制本次运行完成的独立 FIFO 任务数，输入任务、普通 EX 任务及已声明的事务任务都按各自任务身份计数；一次任务正常完成只计一次。显式重试延续原任务，不按尝试次数重复累计完成数。事务中已声明的内部 EX 另记计算量，不自动变成额外调度任务，也不能把原本独立的任务改称内部操作来绕过 FIFO。预算耗尽后不选择新任务，已经开始的任务仍需完成传播边界；故障或资源等待返回对应状态及活动任务身份。
- [ ] `pause` 在当前完整任务结束后停止选择新任务；遇到资源等待或故障时可停止设备工作并保留活动现场，这不表示该任务已经结束。`retry_failed` 只续接保留的活动任务，不把它移到队尾，不越过它处理其他任务。补页、同步、保存、恢复和显式重试属于执行器管理动作，不排到被阻塞任务之后等待执行；它们只能依所声明协议管理现场，不能借此执行另一个模型任务。
- [ ] `read_output` 或等价异步输出接口按逻辑序提供稳定 output_id 和载荷；`snapshot`、资源／诊断查询明确各自 ticket、错误与生命周期。输出复制和应用回调可以异步排空已经提交的记录，回调及外部完成通知若要影响模型，必须形成 FIFO 任务后执行。
- [ ] PyTorch 入口使用 device guard 和调用者 current stream 的 event；输入传输、当前任务执行、输出复制和快照复制可使用不同 stream，依赖必须显式建立。返回 tensor 前建立调用者 stream 的就绪依赖。内部可变状态不作为用户可任意修改的 tensor 别名直接公开；不凭空声明支持 `torch.compile`、自动求导或其他硬件后端。

### 版本与兼容

- [ ] FIFO 完整任务边界、帧格式、事务／环／失败协议使用明确的运行 profile；结构、运行、模块和 CUDA 后端分别版本化。多个 FIFO 的归属、优先级及选择规则必须明确，队内保持 FIFO；物理分片不能自行增加公平轮转或改成另一种选择次序。SCC 预算暂停可在领取任务前阻止相应队头启动，同一 FIFO 的后项不得越过它；其他 FIFO 能否选择按明确声明的规则处理，不由物理就绪先后决定。
- [ ] V5 `draft-1` 与 `draft-2-a03-ready` 分别按各自契约校验并执行兼容语义，不能补造缺失参数或改版本名冒称兼容。旧 profile 的原始 EX、来源和引用、初始化、事件及输出语义保留；V6.1 的独立订阅、状态外置、四类匹配与事务内部依赖，均服从任务先入 FIFO、逐任务执行和完整传播边界。
- [ ] V4 原生恢复、可证明无损迁移、仅导入结构新运行分别给出支持矩阵与迁移报告；缺少的输入或事件历史不能通过默认值伪造。
- [ ] 旧 75 任务及六检查点用于对应的旧契约，不与较早 80／87 节点有限标本混作一个 golden。V6.1 按其已声明的队列选择、输入任务及完整任务边界验证轨迹；采用逐任务执行不意味着不同 profile 的其他语义自动相同。

### 验收与性能

- [ ] **独立语义基准。** 标量参考执行器独立推导 FIFO 选择、参数绑定、节点求值和状态版本；覆盖全部合法 EX、显式 self 的 q_seed、重复引用、参数不足、发布条件和 0。比较任务选择、事件投递、触发配对、目标任务入队、提交及外部输出的完整轨迹。
- [ ] **完整任务边界。** 当前任务的 EX 完成、提交完成或事件记录入队，都不能单独使其结束。注入长扇出和分批传播，确认全部应有投递、匹配更新及目标任务入队完成后才选择下一任务；新形成的目标任务不在传播期间执行。无事件分支、正常无动作和已完成传播分别有明确终止状态。
- [ ] **外部输入与 FIFO。** 当前任务执行或传播期间输入可以被接纳、排队和提前传输，但不得改变节点触发状态或直接产生模型事件。输入任务轮到执行后才消费其锁存载荷并按契约传播。多端口输入按声明次序登记各输入任务；外部任务追加与传播产生的目标任务追加，必须经过可记录、可重放的 FIFO 入队线性化规则。线程抢位、GPU 写槽完成先后和传输完成先后不能替代该逻辑顺序。
- [ ] **事件与资源。** 对 ANY、ALL_LATEST、ZIP、KEYED 检查同源覆盖、重复 key／重复事件、零值、配对状态清空、稳定顺序、分页与容量不足。匹配未齐只保存已到达 token，不等待未来任务产生缺失输入，也不阻止当前任务在完成本次传播后结束。已接纳数据不因队列满或等待配对而丢失。
- [ ] **CUDA 异步与内存。** 对相同的任务入队顺序和队列选择记录，改变 block 大小、当前事件的扇出分块、stream 延迟、H2D／D2H 次序和 allocator 复用；核对状态版本、bit-packed word 更新、事件投递与输出逻辑序。另测真实异步输入的入队线性化；接纳时机改变导致不同入队顺序时，不冒称是同一逻辑重放。
- [ ] **事务与模块。** 覆盖按序事务、事务内前后依赖、资源不足、动态修改／GC、帧宽和块容量、重复帧、跨帧输出、FRAME_OUT 完成控制任务、ACK 译码／陈旧动作、环预算与恢复。已声明原子事务的内部 EX 逐项按序执行；外部改图、完成通知和 ACK 都不能绕过 FIFO 更新模型。验证 SCC 暂停发生在领取前且不会绕过同队队头；快照页面复制和输入载荷准备不能成为执行下一任务的旁路。
- [ ] **故障与恢复。** 注入提交前后故障、传播中断、部分目标任务已入队、宿主接纳后 H2D 前快照、冻结页同时复制、WAL 同步前后崩溃、回复丢失和 outbox 已持久但应用确认丢失。活动任务未结束时后续任务保持排队；重试沿原身份和游标续接，不重复提交、投递或入队。逐一核对 accepted/device_visible/durable、request_id 和 output_id。
- [ ] **CUDA 真实性能。** 在目标 NVIDIA GPU 上测长链短 EX、长 EX、同构／混合模板、高扇出、热点目标、动态增删与持续 I/O；报告端到端完成任务吞吐、输入／输出 p50/p99、当前任务各阶段耗时、kernel／同步次数、host 往返、峰值显存和补页成本。比较 byte/bitpack、解释器/JIT、常驻/有界执行，不能通过同时执行多个 FIFO 任务获取加速，也不能用单个算术 kernel 时间代替完整任务耗时。
- [ ] **双队列专项验收。** 按第 4 节 PERF-P／PERF-X／PERF-H 分别验收传播、EX 和交接，采用 PERF-M 的 E/D/R/G 及独立完成任务计数。覆盖预留未发布、协作写入未完成、槽回绕、满队列、部分扇出续接和故障恢复。批量操作只能处理允许阶段中的记录；任务的批量入队不等于可以批量领取并执行多个任务。队列分片和工作者配比变化不得改变 FIFO 轨迹；容量不足不能通过提前执行后续任务解围。
- [ ] **GPU 专项工具。** 在真实设备执行编译与异步压力，并运行适用的 Compute Sanitizer memcheck、initcheck、synccheck、racecheck；全局内存发布和 packed-word 冲突还需专门压力测试。CPU 参考或静态推导不证明 GPU 内存顺序正确。本方案目前没有 CUDA 环境验证或性能实测，所有勾选项待实现和实际验收。

## 10. 完整性校验与指纹

### 加载和模型校验

- 加载器完整解析注册 profile 中的合法 EX，保留重复操作与原始表达；检测非法残余字符、非法引用、无效常量和输入绑定。兼容 profile 保持其原来的 EX 语法、输入副本、引用下限和全部存活 Q 的引用／DAG 规则；新 profile 按其显式的计算连接、订阅图、状态绑定、数据依赖与环规则分别验证。
- 所有会改变模型业务状态的独立任务具有任务身份、FIFO 归属和明确处理契约。输入、ACK、外部完成控制和结构修改不能以“控制路径”之名绕过 FIFO；纯载荷传输、页面复制、资源管理和显式重试依执行器协议进行，不作为后继业务任务排队，也不据此取得发布新模型事件的权利。
- 节点 ID、世代、程序版本、槽／块世代和分配器高水位分别记录。删除最高编号不得倒退历史分配器；旧绑定不能命中新对象。设备紧凑索引超过范围时切换宽索引或明确报错，不截断逻辑编号。
- 无状态与有状态由 profile 的显式结构／状态绑定确定；旧 profile 按 initial_q 分类，输入副本作为来源时仍按其事件型规则处理。程序优化与共享模板不能更改该分类或订阅。
- 新 profile 的 `PARAM`、`VALUE`、`STATE` 和触发声明必须在形成调用时具有明确绑定规则：例如 ANY 的某一种事件不能提供程序必须的另一个事件参数时，模型需明确从何取得该参数或选择合适的收齐模式；加载器不得把缺失值当作 0。编译化简不得静默删除契约要求的来源、可取得性检查或触发订阅。

### 指纹与规范化

- V5 兼容 profile 严格采用其对应版本已定义的规范字节和结构／格式指纹 F、完整运行指纹 M；结构与初值、契约等按旧规则参与 F，运行状态按旧规则参与 M。数组保序，只归一化对应规范允许的默认值，不把任务内 `cause` 误当成根部展示 metadata 排除。
- V6.1 的 FIFO 运行、事务、环与失败 profile 各自声明格式修订、规范化规则、哈希算法、字段范围和测试向量。状态版本、触发剩余、各 FIFO 的逻辑记录及顺序、队列选择配置、唯一活动任务与阶段、归属于它的事件和部分传播游标、提交／发布进度、输入输出前沿、预算和事务现场，按相应 profile 进入完整运行指纹。物理分片、空槽、可重建的 head/tail 和工作者数量不改变逻辑身份。
- 普通快照对应完整任务边界；异常现场还必须保存尚未结束的唯一活动任务及可续接进度。未提交任务与已提交但传播未完任务不能使用同一种恢复动作。恢复成功后暂停安装，由显式运行或重试继续，不自动执行任务或补造事件。
- 验收应核对：改变当前 q 影响完整运行指纹；改变 EX 或结构影响相应结构与运行指纹；改变 FIFO 顺序、活动任务的传播游标或输入任务载荷会改变对应运行现场；改变纯设备页布局不影响逻辑指纹。保留高水位、队列顺序、key、输入输出游标及活动任务身份后，恢复的规范化结果一致。不得默改旧摘要规则或仅凭摘要替代字段、世代和引用校验。

### 确认状态与验收状态

全文中“已确认”表示用户已批准且未被后续明确指令替换的方案。最新确认的调度边界为：所有任务先进 FIFO；每实例一次执行一个任务；只有该任务的执行、提交、应有事件传播及目标任务入队全部完成，才结束它并选择下一个。`[ ]` 是实现和验收进度，供填写结果，并非要求再次批准。未来会改变已批准对外行为的新提案应单独标出，不因技术上可行自动生效。本文的 CUDA 结构、伪代码与容量协议均为设计，真实设备编译、内存顺序、故障注入和性能测量尚未执行。
