# JK CUDA 实现方案 V6.1

> 状态：本方案中标为“已确认”的模型和运行语义，已由用户在本轮讨论中批准；CUDA 内核、运行时和恢复实现尚未编写或在 GPU 上验证。本文不把性能预测或人工推导写成实测结论。

## 1. 目的、范围和阅读方式

本方案面向单个大型 JK 模型、单张 NVIDIA GPU，采用 PyTorch CUDA 张量、自定义 C++/CUDA 内核及必要的宿主 I/O 和资源管理。JK 规则是设计来源；用户已明确允许为适配 CUDA 调整节点、触发、并行、事务、环和保存恢复语义。V6.1 新运行 profile 与 V5 兼容 profile 分开定义，不能把新行为称为旧 JKRD 已有规则，也不能将旧设计的首版限制当成 V6.1 的默认边界。

本文按“输入 → 触发 → 调用 → 并行计算 → 事务提交 → 传播与输出 → 保存恢复”组织，并在各模块列出方案、边界和验收点。模块编号用于标注和追踪；原 V6 的 A01–H04 对照见文末。用户可在任一模块下追加“标注：……”；追加标注不自动更改已确认的语义。

来源基线为用户提供的 `plan.V6.md` 及其引用的 `DRAFTS--V5.0.0@0a8cc58c882dac1b1c1af21b304cb18c7afe2010`。其中 V5 的 75 任务、六个检查点是候选设计及人工推导，不代表 CUDA 执行或恢复已验证。V6.1 的新方案以本次会话中已确认的 N01–N06、M01–M12 及最终补充为准。

## 2. 全局结构与运行流程

```text
JK CUDA 实例（单张 NVIDIA GPU）
├─ 模型和编译
│  ├─ 逻辑节点：共享程序模板 + 来源绑定 + 可选状态槽 + 触发契约
│  ├─ 计算连接与触发订阅分开；稳定 ID／世代映射到设备槽位
│  └─ 校验 → 编译或解释 → GPU SoA 数组、稀疏连接和页池
├─ 接入
│  ├─ CPU 输入或 CUDA tensor → 校验与预留 → 不可变载荷、输入序号
│  ├─ accepted / device_visible / durable 独立报告
│  └─ 封存输入前沿；通过 stream event／设备发布协议交接
├─ 设备执行
│  ├─ ANY / ALL_LATEST / ZIP / KEYED：事件积累与调用形成
│  ├─ 封存有界逻辑组 → 状态与数据依赖 → 并行波次
│  ├─ 绑定实际版本 → GPU EX/计算块求值 → 事务候选与冲突协调
│  └─ 按逻辑次序提交 → 生成稳定后继事件和输出记录
├─ 业务模块
│  ├─ 可配置帧宽与存储块、前后业务接入、帧世代与 ACK
│  ├─ 动态创建、连线、改 EX、退休回收
│  └─ 事件反馈环、依赖环检查和预算监督
└─ 对外交接与运行保障
   ├─ GPU 输出 → D2H → 宿主 outbox → 应用接收／回调
   ├─ 资源背压、局部故障、显式重试、设备故障恢复
   ├─ 一致快照 + 可选持久输入日志／提交日志／输出箱
   └─ 兼容 profile、独立参考、真实 GPU 正确性和性能验收
```

**已确认的关键行为：**逻辑状态在执行时绑定；显式连接可以依赖前序结果；并行调用受状态槽和版本依赖约束；执行组封存后，新的输入进入后续选择；事务内部允许前后计算依赖，冲突按逻辑顺序处理；事务具有独立逻辑提交；新输出接口允许携带帧 ID 和位置跨帧交错，旧的无帧 ID 接口按帧连续；KEYED 同 key 同来源按 FIFO 配对；ACK 译码时绑定具体帧；环按逻辑调用次数监督；支持局部故障隔离、显式重试和可选持久模式。

这些是实现目标而不是已运行功能。对同一组逻辑封存记录和输入前沿，设备内线程、CUDA block、物理 batch 和 kernel 完成先后不得擅自更改逻辑状态版本、事件顺序或对外结果。对按真实时间异步到达的输入，设备速度变化可能改变它属于哪个封存前沿；验收须区分重放同一前沿和真实异步接入两类情况。

## 3. 节点、连接和 CUDA 执行

### 整体关系与执行边界

```text
模型定义 / 结构更新
├─ 逻辑节点：计算程序、参数绑定、可选状态、触发契约
├─ 计算连接：CONST / STATE / VALUE / PARAM
├─ 触发订阅：来源事件 → 目标、输入位置、配对模式
└─ 编译器：合法性检查 → 设备数组 → 共享程序模板
     ↓
输入提交 / 内部事件
├─ 校验和资源预留 → 接纳序号 → 不可变载荷
├─ 异步传输与设备发布 → 设备可见
└─ 可选持久日志 → durable 确认
     ↓
有界逻辑执行组封存
├─ 固定输入前沿及已形成的就绪调用
├─ 事件按目标、逻辑序号处理 → 满足触发条件的独立调用
├─ 按状态槽和版本建立依赖，形成可并行波次
└─ 每波：绑定参数和 q 起点 → CUDA 并行求值 → 冲突协调与提交
     ↓
按逻辑序登记后继事件和输出 → 完成本组边界 → 选择下一组
```

- 设备执行器允许多个无依赖调用并行；不得把旧“整个实例只有一个活动节点”作为通用约束。
- 逻辑执行组是可观察的选择边界；对已经确定的组封存记录和输入前沿，CUDA block、kernel 切分和临时缓冲区容量只影响物理执行，不能反向改变组成员、状态版本、事件或输出顺序。
- 正常结束的组处理其规定的提交和传播后，才选择下一组。组内调用在设备上按依赖分波，同一事务内部可由前一步暂存结果驱动后续步骤；该内部依赖并不等于让未就绪的外部调用执行。
- 新 profile 的组选择读取明确注册的优先级和公平策略；策略、配置和可影响后续选择的运行状态必须进入快照。封组后不因新输入抢断该组；线程抢位不能决定优先次序。持续高优先输入可能造成低优先级饥饿，除非该 profile 明确启用公平策略。具体三队列、自动轮转或公平配额不因物理实现而默认启用。旧 V5 兼容 profile 仍按其原 `Xi→RAM→Qi` 严格优先和逐任务边界执行；这是兼容语义，不恢复新 profile 的全局单活动任务限制。
- 不等待组凑满；当就绪数少于组上限时立即封存。`run(max_tasks)` 的剩余预算参与封存。一个原子调用超过普通组预算时单独执行、补充资源或明确报资源故障，不能反复生成空组。
- 组发生可恢复的局部失败时，账本记录已完成、失败保留和依赖阻塞；独立分支允许继续，失败不被伪装成全部成功。`step` 对应一个逻辑执行组，并可报告部分失败。

### JK 最小算子与节点结构

**方案 N01-1：统一计算 IR，状态存储外置。**

```text
基础计算：r = (q AND a) XOR b
J(x)：a=x，b=0       → q AND x
K(x)：a=1，b=x       → q XOR x

逻辑节点 = 程序模板 + 来源绑定 + 可选状态绑定 + 触发契约
```

1. 状态节点的起点从绑定状态槽读取；无状态计算可使用常量或其他值作为起点。普通计算中间值留在寄存器，不强制为每个算子建立全局状态槽。
2. 单条 J/K 指令可紧凑表示为 `(op, source_index)`，J 的 `b=0` 和 K 的 `a=1` 无须逐条存储。CUDA IR 可将两者统一编译为三输入布尔函数；能否生成目标 GPU 的 `LOP3` 指令以实际编译结果为准。
3. 完整 EX 可以保留为上层定义，多个 EX 可在满足依赖和可观察性要求时融合。编译结果与原始 EX、程序版本、源引用元数据分开保存，以便导出、审查和旧 profile 恢复。
4. EX 内相同来源引用按该次调用的固定值计算。显式 `self` 与隐式 q 起点均绑定该调用开始时的旧 q，不读取 EX 内不断变化的累加器。
5. 优化器可按代数简化计算，但不能擅自删除触发订阅或已声明的输入要求。旧 profile 维持原 EX 的参数可取得检查；新 profile 按显式参数和触发契约校验。条件不发布或未取得参数等分支必须明确完成，不留下无法推进的执行记录。
6. 可配置的结果发布条件基于该次调用的结果及其版本判断，不在延迟发布时回读最新状态。重复同值调用保持各自身份；是否发布由对应契约决定。初始化和恢复不自动伪造事件。

**方案 N01-2：来源和状态直接表达。**

| 来源类型 | 含义与绑定时机 |
|---|---|
| `CONST` | 布尔常量。 |
| `STATE` | 独立状态槽；逻辑执行时按依赖绑定确定版本。 |
| `VALUE` | 某次计算结果的不可变版本，可用于显式前序依赖或事务内部暂存结果。 |
| `PARAM` | 本次输入、事件或其他调用绑定的不可变参数。 |

计算来源、状态写入、触发订阅使用独立描述。触发来源可以不参与算术；节点应通过参数契约明确哪些值必须可取得，不能因为触发到达就假设其他参数已齐。无状态节点不会仅因设备分配了临时值槽而变成有状态节点。

**CUDA 表示。** 状态值、节点信息、程序偏移、操作数绑定、订阅边和调用描述分别放在设备 SoA 数组。使用稳定逻辑 ID、世代、程序版本与设备槽位映射；物理搬页或分组不改变逻辑身份。索引使用经过容量校验的紧凑表示，超出范围时采用宽索引，禁止截断。相同程序共享模板和编译缓存，单个调用仍持有独立参数与状态绑定。

### 输入和设备接入

**方案 N02：输入可直接绑定参数及触发事件，不强制设置同编号复制节点。** 同一 `send` 中每个端口按声明顺序拥有独立的输入记录和不可变数据；多提交者的接纳按序列化入口分配唯一序号。单次提交是完整接纳或拒绝，重复相同 bit 的不同请求仍是不同输入。

```text
CPU 输入：校验/预留 → 接纳 → pinned 缓冲 → 异步 H2D → 设备发布
CUDA tensor：生产者 stream event → 校验/复制或接管 → 设备发布
```

- 状态分别报告 `accepted`（宿主已接纳）、`device_visible`（设备可读取）、`durable`（持久确认）；后两者可以先后独立完成，不能将一次异步复制调用返回视为设备可读或已落盘。
- 运行时捕获组的接纳前沿 F。F 内仍在 H2D 的输入，须等待对应 CUDA event 并按顺序交接后参与本次选择；F 后的新输入进入后续选择。捕获前沿的短锁不跨 GPU 计算或文件持久化。
- 接入数据在消费者结束前必须不可变。`record_stream` 只保护生命周期，不防止调用者修改 tensor，也不能替代跨 stream 依赖；必要时复制到运行时拥有的载荷区。异步设备校验尚未完成时接口返回 pending，检查通过后才能声明接纳。
- 允许 CPU 输入与已在 GPU 上的 tensor 输入；生产者 stream 通过 event 与运行时 ingress stream 衔接。无条件对每条输入做主机同步不是主执行路径。

### 触发、到达集合和调用

**方案 N03：执行器以 GPU 元数据维护触发与就绪，支持四种显式配对模式。**

| 模式 | 设备状态及语义 |
|---|---|
| `ANY` | 每次满足订阅条件的事件形成独立调用；不合并重复值。 |
| `ALL_LATEST` | 每个来源记录到达有效位和值；未齐期间同源新值覆盖，收齐后形成一次调用并清空当前组。 |
| `ZIP` | 每来源保留未消费事件的 FIFO，按来源内顺序逐项配对。 |
| `KEYED` | 按明确业务 key／帧 ID 分桶；同 key、同来源使用 FIFO，按顺序配对。 |

四种模式的状态、载荷所有权、剩余队列和容量单独记录；0 是有效值，不能当作未到达。CUDA batch 编号不作为业务帧或 key。

**确定性 CUDA 管线。**

1. 生成 `(target, source_position, event_seq, value, key)` 记录，事件序号由逻辑发布次序确定，不能由线程抢到的原子下标决定。
2. 按目标和逻辑事件序号稳定分组；每个目标由独占处理者依序更新到达状态，避免 `atomicOr` 后清零与下一组事件竞争。
3. 每次收齐的位置生成独立调用；使用计数、前缀和与 scatter 构造连续可执行列表，并按原逻辑位置恢复跨目标顺序。静默、跳过、失败的调用须推进游标或写明确终止记录。
4. 同一批 `A=0、B=1、A=1、B=0` 对 `ALL_LATEST` 必须形成 `(0,1)` 与 `(1,0)` 两次调用，不能在目标分组时仅保留每来源最后值。
5. 事件个数、扇出和临时空间先计数并预留。超过容量时稳定分波或请求补页，保留未处理游标；禁止先公开部分结果再截断。ZIP／KEYED 的等待不能占住当前组直到未来组才可能提供的业务输入；已接纳 token 必须有容量归属，内存不足进入明确背压／资源故障。

**标注 R01｜逻辑事件合并顺序待确认：**上一组的内部后继事件与该组运行期间由宿主接纳、在下一组前沿内的输入，可能同时到达同一目标；此前批准了两者各自的逻辑顺序，但未定义它们之间的合并次序。一个可审候选是先按上一组的调用／发布次序处理后继，再按输入接纳序号和端口次序处理输入；另一个候选是为两类事件建立可重放的统一顺序。这个选择会改变 `ALL_LATEST`、`ZIP` 和 `KEYED` 的配对，不能由 GPU 线程抢位或 kernel 完成时间决定。profile 确定后须写入契约和快照／日志，并以同目标混合输入与内部事件、不同物理 batch 和重放进行验收；在规则未确定前，不能宣称该混合情形已完整定稿。旧 V5 兼容 profile 按原契约执行。

调用描述至少绑定程序版本、输入引用及其版本、起点／状态读取版本、可选状态写入槽和结果身份。每次执行的参数固定后不受后来输入或状态变化影响；共享只读载荷可按批次持有，避免逐 bit 对象与逐边复制。

### 执行组、依赖和 GPU 提交

**方案 N04：封存有界逻辑组，按依赖驱动并行。**

```text
组封存 → 根据状态槽+版本和显式 VALUE 依赖形成波次
       → 绑定本波参数 → 并行执行共享模板 → 汇合/提交
       → 按逻辑序登记结果、事件和输出 → 组结束
```

1. 不同状态槽且无数据依赖的调用可以并行；多个调用写同一槽按确定逻辑顺序串接，不能让最后完成的线程获胜。可支持明确声明的结合归约，但普通写入不自动合并成归约。
2. 读后写、写后读和写后写关系均以状态槽及版本判断；别名节点共享槽时必须进入同一冲突链。组内 A 写 S、B 依赖 A 的新 S 时，B 在后续波次绑定。B 明确读取旧版本时可并行。
3. 下一组的状态绑定等待当前组规定的最终提交；输入传输和输出复制可以与计算重叠。新增输入在下一次选择生效，不要求 GPU 正在运行的组中途逐节点抢占。
4. 每次 EX 持有自己的只读参数、起点和结果。事务内部显式前后依赖使用暂存结果；事务外可见性由事务提交控制。条件无动作、静默结果及失败都必须解除或明确阻塞相应依赖，不让工作计数永久不归零。
5. 组完成条件涵盖本组已封存调用、事务内部依赖波次及尚在完成的提交和传播登记，不能仅检查 ready 队列是否为空。生成的新调用登记到独立的 `next_ready`，其拥有权和容量由下一组管理，不计入当前组尚未完成的调用；生产者先完成后继登记，再递减本组工作计数。只有组已封存、本组计数为零且提交与传播登记完成，才允许结束本组并选择下一组，避免当前组等待只能由下一组执行的工作而死锁。
6. 逻辑序号按组内调用与发布位置确定；并行 kernel 和 stream 的实际完成先后不改变逻辑序列。检查物理分组与启动参数变化时的可复现性。

**设备计算落点。** 短 EX：同模板的一组调用由多个线程并行，每线程将 q 保存在寄存器并完成一个程序。热点模板可生成专用 kernel；通用设备解释器始终覆盖合法程序，JIT 未命中影响速度而不影响支持范围。长 EX 可由 warp 按顺序组合运算，但 J/K 组合不可交换，归约必须保持原顺序，尾部填充恒等变换。算术并行不能消除动态来源的 gather 成本。

以下是已绑定参数的同模板短 EX kernel 示意；`seed` 和 `inputs` 已完成 0/1 校验及版本绑定，`active_count` 不超过预留容量。它只写结果数组，状态和事件由后续 kernel 提交，尚未在 GPU 编译或测量：

```cpp
__global__ void eval_program(
    const uint8_t* seed, const uint8_t* inputs,
    const uint8_t* op_kind, const int32_t* op_arg,
    int32_t op_count, int32_t capacity,
    const int32_t* active_count, uint8_t* results) {
    int32_t i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= *active_count) return;
    uint32_t q = seed[i];
    for (int32_t t = 0; t < op_count; ++t) {
        uint32_t x = inputs[(size_t)op_arg[t] * capacity + i];
        uint32_t k = op_kind[t]; // J=0，K=1
        q = (q & (x | k)) ^ (x & k);
    }
    results[i] = (uint8_t)q;
}
```

计算块可融合多个纯计算节点，中间值保存在寄存器；已经声明的状态写入、触发或可观察输出位置需保留。不能把 `__syncthreads()` 当成全 grid 的同步；跨 block 阶段使用 kernel 边界、受支持的协作机制或显式依赖。

### CUDA stream、内存与前进性

**方案 N05：PyTorch tensor 作为设备数组的所有者，C++/CUDA 扩展管理执行。**

- 使用 device/stream guard，执行器单独管理输入、计算和输出 stream；输入生产、参数绑定、计算、提交、输出复制通过 CUDA event 或经核实的设备 release/acquire 建立依赖。对用户返回的 tensor 建立当前 stream 的就绪依赖。
- 有界 kernel 或固定容量 CUDA Graph 都可运行已批准语义；设备 count、valid 位和预分配工作区用于处理动态负载。常规 CUB 排序、选择接口的 `num_items` 往往是宿主参数，不能假设设备 count 可直接替代；可用固定容量 bucket＋无效项排序，并在容量变化时切换或重建 graph。
- 常驻 worker 不能无限等待另一个可能无法获得资源的发布 kernel。CUDA 不保证不同 stream 的 kernel 一定并发或公平；无就绪任务、预算耗尽或等待补页／输出时保存续接并让出。仅“预留 SM”不能作为正确性保证。
- 独立 NVRTC 模块不会自动被已编译的常驻 kernel 内联。专用程序可在安全边界按模板 bucket 作为 kernel 调度，或安全切换完整 dispatch；旧模块、graph 和 tensor 保留到最后一次使用完成。缓存键包含程序、ABI、编译器版本、GPU 架构和布局。
- 可变 bit 打包状态中，不同 bit 写同一机器字仍会发生读改写冲突。使用整字独占写入者、合并掩码或适当原子操作；只读载荷和对齐同构计算可用位切片。是否采用打包由端到端测量决定。
- GPU 状态、边、事件、参数、输出和候选数据使用分段池。设备从已有池分配，宿主批量补页；不能在捕获的执行热路径中假设可无限扩展 tensor。引用、世代和 CUDA event 共同决定槽位回收。
- 校验失败、容量不足、异步 CUDA 错误和致命设备故障分别报告。正常数据拒绝不使用会污染上下文的 device assert；非法访存、device assert 或设备丢失不按普通 OOM 原地重试。

**验收关注。** 用逻辑轨迹比较不同 block 大小、物理分波和 stream 延迟下的状态版本、触发配对和输出顺序；测试相同槽别名、同一字不同 bit、事件分组与容量溢出。性能测量包括输入接纳、绑定与 gather、事件分组、kernel、提交、输出交接和峰值显存，而不只测单 kernel。实际 CUDA 编译、运行、Compute Sanitizer 和 GPU 性能尚待目标环境验证。

## 4. 事务、动态结构、帧存储与环监督

以下为已批准架构的具体实现方案。业务语义由运行 profile 和模块契约声明；物理页、CUDA stream 和执行线程只是实现，不构成新的业务顺序。代码、GPU 运行及性能尚未验证。每个条目的“标注”供后续补充问题、修改或验收结果，不表示需要重新批准已确认的方向。

### 事务与动态结构总览

```text
逻辑调用或模块请求
├─ 绑定 TxDesc：事务 ID、契约和程序版本、输入及状态版本、操作清单
├─ 构造内部依赖 DAG
│  ├─ 外部参数和目标身份：执行前实际可用
│  └─ 前序 EX 的事务内结果：以暂存 result/version 供后续 EX 使用
├─ 确认逻辑读写次序与保护
├─ 预估并预留候选页、队列、事件、输出及临时工作区
├─ 一个或多个 GPU 波次：bind → evaluate → 产生候选写集
├─ 提交协调器：校验版本、按槽合并写集、安装候选版本根
└─ 依序传播和宿主交接；旧版本等待所有持有者释放后回收
```

#### T01　事务描述、内部依赖和逻辑提交

- **设备数据：**`tx_desc[]`、读写目标与版本、`planned_creations[]`、结构增删、EX 调用序号、结果引用、资源清单、发布意图及状态标记采用分段设备数组。每个事务、每次内部 EX 都有稳定逻辑身份；地址只是定位方式。
- **输入与结果：**事件锁存参数和状态槽版本分别记录。事务外提供的参数及对象身份在使用前必须实际可用；事务内部允许后序 EX 依赖前序 EX 的暂存结果。内部依赖用显式 `result_ref` 表示，后续波次等待前序结果就绪，不能把未来结果写成已经产生的输入。
- **q 起点和自引用：**每次 EX 开始时的隐式旧 q 和显式 `self` 读取同一个固定起点，不能指向中途变化的寄存器累加器；读写依赖按 `state_slot + version` 计算，不按节点 ID 猜测。状态槽别名必须进入同一个冲突关系。
- **并行与可见性：**无依赖或无冲突事务可并行准备和计算。每个事务具有独立逻辑提交身份；条件失败、取消、回滚和已提交状态在设备账本中分别记录。为减少开销，GPU 可以合并无冲突物理写入，但生成的事件顺序、外部可观察结果和故障恢复必须等价于各事务按规定逻辑顺序提交；不能因批量优化改变事务边界。
- **stream 依赖：**上传完成 event 约束求值；各求值 stream 的完成 event 汇入提交 stream；根版本安装完成 event 约束后继读取、传播及输出。`cudaEvent` 只证明该 event 之前在相关 stream 排入且受依赖约束的工作完成；Python 调用返回、device 标记或某个无关联 stream 的完成都不能代替此判断。
- **失败隔离：**提交前失败释放该事务未安装候选并保存已绑定参数；已提交事务不重算，后续按已记录进度继续传播和交接。组账本记录成功、失败保留、依赖阻塞，独立事务继续前进；设备致命错误属于 CUDA 工作域故障，另按恢复协议处理。
- **验收：**并行独立事务、串接事务、同状态槽别名、内部多 EX 依赖和多次同目标调用均按声明版本求值；注入任何准备阶段失败后不能出现部分结构或提前输出。标注：_______。

#### T02　跨事务候选页与版本根

- 根描述符引用状态页表、节点／EX／连接版本、触发集合、调用及输出等逻辑现场。输入接纳追加区和其前沿单独管理，切换根时不能用旧快照覆盖并发接纳的新输入。
- 修改页使用候选页和分层页表；读者持有已绑定版本。候选校验完成后，设备协调器按事务逻辑顺序发布根索引／版本；跨 kernel 依靠 stream 次序及 event，跨并发访问需要明确的 device 级发布和读取同步。
- **同页不丢写：**若原页含 `A=0,B=0`，事务一写 A、事务二写 B，不能分别安装 `[1,0]` 和 `[0,1]` 两张完整页。协调器按逻辑槽合并 dirty patch，检查基版本，对同页生成能保留两次合法写入的候选；同槽写冲突依照逻辑依赖顺序处理。
- 版本根切换之前，传输、事件、输出区及后继所需空间均已预留；容量不够则保持当前提交版本并进入补页／背压或明确资源失败。后继和输出不得只形成一部分后宣称事务提交完成。
- **验收：**改变事务准备与 stream 完成的物理先后，同页不同槽的合法结果不丢写；同槽冲突顺序不由线程抢位决定；后继或输出容量不足不会公开半提交。标注：_______。

#### T03　节点、边、版本与生命周期

```text
逻辑身份：Node ID + generation + program version
    ↓ 映射
设备槽位／状态槽／程序模板／连接表页
    ├─ 计算来源索引与触发订阅索引分开
    ├─ 稀疏 CSR 基表 + 已提交增删 delta + 存活信息
    └─ 候选新版本经校验后安装；旧版本按持有者生命周期释放
```

- GPU SoA 分别保存节点、状态、程序、操作数、订阅边、事件与版本映射。新连接表由 kernel 在候选缓冲区构建；compact/scan 重建 CSR 时，执行中的调用继续持有旧表。事件按它形成时绑定的订阅版本处理，物理搬页或排序不改变逻辑身份。
- 改 EX 先安装新的不可变程序版本；解释器可运行新程序，热点内核缓存按程序 ABI、模板、设备架构和版本失效或切换。代码模块和底层数组要等最后使用它的 stream event 完成后才卸载或回收。
- 删除分为逻辑退休和物理回收。保护范围包括在途调用、锁存事件、状态读版本、输出载荷、事务暂存和快照；静默节点同样需要检查真实引用。新订阅或新对象不会接收不属于其绑定版本的旧事件。
- 块或槽复用时先解除全部持有，再推进相应 generation；旧调用、旧帧、旧 ACK 不得命中新对象。逻辑编号可有空洞；设备索引宽度按容量选择并检查溢出，不得截断身份或发生世代回绕。
- **验收：**同槽别名、旧程序调用与新程序并存、CSR 重建时的旧订阅、删除高编号后再创建、帧槽重用均不改变旧绑定或令旧句柄命中新对象。标注：_______。

### 异步帧、输出与 ACK

#### S01　参数化帧存储与计算接入

```text
输入帧（Frame ID、W、位序、接纳序号、不可变载荷）
  → 设备帧槽与前态表
  → 就绪／领取控制
  → GPU 业务计算块
  → 原子写回结果与后态
  → 帧输出批次与资格建立
```

- 新模块按配置支持帧宽 `W` 和块容量 `K`，同时为数据槽和元数据预留显存；宽度超过机器字时使用多字或分段表示，物理页大小不等于业务块容量。输入帧保留实际 W、帧身份、位序和独立载荷，不能从最新输入重拼旧帧。
- 旧模块 profile 按其契约保留 W=1–8 和每块每世代八个接纳槽；满八、全部消费且依赖解除后才允许整体释放／复用。新模块的容量与复用范围由其声明契约确定，槽级复用必须有槽世代，不能只依赖整块世代。
- 领取、队首推进、到达和就绪可以由 CUDA 控制数组与 kernel 实现；业务计算程序仍由约定的节点算子／计算块产生。控制元数据与业务结果的责任在模块契约中明确，不能把不相关的缓存当成真实计算结果。
- 保持历史帧计算含义时，按宽度保存 `S_W/C_W`，不能悄悄把全部宽度共享一份 C。零值、相同 parity 和重复帧都要按各自事件和帧身份处理，不能因计算值相同而去重。
- 声明式业务 DAG 必须列出输入输出、跨轮状态与依赖，生成 PRE／领取／计算／提交／POST 等设备程序。多个帧能否并行取决于其显式状态依赖；共享状态的写入按已绑定的版本顺序推进。
- **验收：**W=1、8、超过 8，部分使用块、满块增长与合法复用、重复 0 和相同 parity、不同宽度交替输入，均保持载荷与世代正确；旧 profile 的满八条件不被新 K 覆盖。标注：_______。

#### S02　输出批次、完成标记和外部交接

- 每个输出批次在锁存后拥有自身的 frame ID、帧世代、实际宽度、数据位与 marker 载荷；旧数据槽释放或新帧覆盖不能改变已锁存批次。
- GPU 执行输出节点／计算块后生成不可变输出记录；逻辑序号由已封存的调用顺序、发布顺序和稳定压缩结果确定，不用线程完成或原子抢位顺序。结果是否发布按该次调用的结果与对应契约判断，不能延后读取状态槽的最新值。
- 路径为设备记录 → 等待关联计算／提交 event → D2H → 宿主 outbox 接管 → 应用处理。排空线程独立于应用回调；回调不能持有输入接入、提交或输出环锁，也不能因失败重跑已提交 EX。
- V6.1 新 profile 中，`FRAME_OUT` 对应的外部交接点是宿主接收完成：该帧实际 W 个数据记录先成功交接，随后 marker 才完成交接。宿主把带 frame ID、世代和输出身份的完成控制记录按逻辑输入次序传回 GPU；资格只在对应控制记录被处理后建立，不能在 D2H 完成前由设备提前假设已接收。旧 V5 兼容 profile 的资格和完成边界按其原契约执行，不能将新 profile 的控制记录协议强加给旧检查点。
- 宿主将 marker 交给应用前，先确保其完成控制记录已进入可靠的逻辑接入序列；需要专用控制容量或预留空间，避免普通输入背压使 marker 完成与 ACK 相互等待。GPU 内部看到完成记录的时点、宿主接收时点和外部业务 ACK 是不同事实，分别留痕。
- 已批准的新输出接口允许不同帧交错，每条记录带 `frame_id` 和帧内位置；同帧数据的顺序与 marker 依赖保持正确。旧不带帧 ID 的接口按帧连续输出，避免接收方无法区分帧边界。设备执行顺序不能代替逻辑发布次序。
- **验收：**W 个数据均完成前不能形成该帧 marker 完成；用户回调阻塞或再次 `send` 不死锁；物理复制顺序变化不打乱逻辑输出；新接口可区分交错帧，旧接口帧内连续。标注：_______。

#### S03　ACK 译码、资格与动作

- ACK 输入保留独立 ID、锁存值和接纳顺序。DEC 在其**逻辑执行时**读取当时队首、frame ID、槽／帧世代及资格；成功后形成携带明确 `FrameRef + generation + qualification_token` 的 ACT。
- ACT 验证先前绑定对象；已消费、已重用或资格不再匹配则无业务效果，不重新选择下一帧。允许执行 ACT 的真实状态变化与队首推进在所声明的事务边界提交，不能由线程抢先决定。
- 资格零是有效值。DEC 看到资格为零时按当前契约无动作，不挂起等待未来资格；同一帧的两个 ACT 若第一个已消费，第二个不可消费后继帧。旧重发或旧 FRAME_OUT 的迟到完成不得复活已消费资格。
- ACK 到达时间和 DEC 执行时间分别记录：一个 ACK 可能在 FRAME_OUT 宿主交接前被接纳，但在后续执行阶段才译码；如果逻辑上它译码时已导入对应交接完成记录且资格有效，该 ACK 可以成功。不能仅凭物理到达早于 marker 推断一定失败。
- ACK0／ACK1 的业务含义、首发与重发、数据保留和资格撤销写入模块契约；输出载荷与外部交接确认不冒充业务 ACK。多个在途帧的资格不能只用一份全局奇偶标志替代。
- **验收：**FRAME_OUT 前译码被忽略；先接纳后译码且译码时合格按契约生效；两个 ACT 绑定同帧只消费一次；槽复用后旧 ACT 不命中新世代；旧完成和重发不能复活资格。标注：_______。

### 环、监督与动态回收

#### L01　环的识别和运行预算

```text
建图或结构提交
├─ 计算数据版本依赖图：检查是否有可启动的初值／延迟边
└─ 计算触发订阅图的 SCC：记录 SCC 身份、成员、调用预算和状态
   ├─ 依赖齐备：选择可执行调用，预算按逻辑调用计数
   ├─ 达到预算：暂停该 SCC，保留事件、绑定版本与未完成工作
   └─ 明确恢复：继续保存的现场并开始所配置的后续预算段
```

- 允许事件反馈环。拓扑变化后重新检查受影响子图；订阅图的环和计算／版本依赖环分别判定。没有初始令牌、初始状态或延迟边可使之启动的数据依赖环，必须提供明确的启动规则或在加载／改图时拒绝；单纯设置执行预算无法让它就绪。
- 预算按实际逻辑调用计数，包括融合到一个 kernel 中的多个逻辑调用。封存执行组时考虑每个 SCC 的剩余预算，避免多个并行调用同时越过上限；达到上限保存待处理事件、当前预算和暂停状态。
- 暂停该 SCC 不自动清除任务、载荷或数据；无依赖的其他 SCC 可以继续。显式恢复继续同一现场并按配置进入新预算段，已累计的历史计数和原因可供诊断；快照恢复不应隐式重置或丢弃它们。
- 动态改图时若 SCC 合并、拆分，候选结构、尚存事件、旧预算和暂停状态一起检查，映射规则写入模块契约；不能仅凭物理槽变化把活动环当作全新历史。
- **验收：**含状态反馈、无初值数据环、并行调用接近预算边界、暂停时新事件到达、SCC 合并拆分及快照恢复都保留正确的事件、版本与预算；长时间无结果不能自动断言为死环。标注：_______。

## 5. 输入、输出与宿主交接

```text
输入调用
├─ 校验数据与身份、预留完整资源、取得不可变载荷
├─ accepted：宿主接纳成功
├─ H2D 或设备到设备传输 → device_visible
├─ 可选日志同步 → durable
└─ 组封存前沿内的输入进入本组选择；之后的输入进入后续选择

GPU 输出记录
├─ CUDA 提交与依赖 stream 完成事件
├─ 复制或移交至宿主独立接收区
├─ 宿主接收完成：对外交接
└─ 应用读取／回调；业务 ACK 单独执行
```

### 输入协议

- [ ] **接纳边界。** 每次提交拥有独立 input_id、端口及值、来源身份；整次输入校验、容量预留和不可变载荷所有权取得成功后才确认 `accepted`。多端口输入按契约固定次序逐项形成事件，不能只复制最新端口值。0、重复输入都是有效且独立的事件。
- [ ] **三个确认点。** `accepted` 表示宿主持有不可变输入并承诺在当前运行中接续；`device_visible` 表示完成传输且设备发布记录可读；`durable` 表示持久日志已完成所约定的同步。后两者可按任意顺序发生，分别查询，不把 `cudaMemcpyAsync` 返回当传输完成，也不把内存接纳冒充持久承诺。GPU tensor 的异步合法性检查结束前，ticket 保持 pending；检查失败返回 rejected，不先返回成功。
- [ ] **封存与 CUDA 同步。** 组选择捕获不可变 `accepted_frontier`；该前沿内已接纳但 H2D 未完成的输入，等待其 CUDA event／已验证的设备发布握手后参加选择。后接纳的输入进入后续选择。capture 接纳前沿时短暂持接入锁，不能在锁内等待 GPU、日志或应用。
- [ ] **所有权。** pinned host 缓冲区必须留存到 H2D event 成功；设备载荷保留到全部消费者完成。直接接入 CUDA tensor 时，在生产者 current stream 记录事件，执行器 stream 等待事件，并按需调用 `record_stream` 或持有引用以防 allocator 提前复用。运行时复制或明确接管不可变载荷；`record_stream` 既不能阻止调用方改写 tensor，也不能代替跨流就绪依赖。
- [ ] **容量与配对。** 输入描述符、载荷、触发目标和可能的临时空间纳入接纳前预留与水位控制；必要时拒绝或背压，不能部分接受。ZIP/KEYED 的某一来源积压不能令当前组等待未来组的另一来源；令有效 token 成为分页队列元素、维持匹配来源的推进能力，显存实际耗尽时上报资源故障或等待补页，不丢已接纳事件。

### 输出协议

- [ ] **设备到宿主。** 计算调用结果和事件通过逻辑顺序编号；提交 stream 与相关执行 stream 的完成事件汇合后，egress stream 才复制已提交记录。宿主确认 D2H 成功并获得独立不可变记录后，才算本接口的外部交接；不能凭设备内根标志或 Python 调用返回判断交接成功。
- [ ] **解耦回调。** 独立 drain 路径将已完成设备记录移交宿主 outbox，释放设备输出槽；应用回调或读取在独立路径运行，不能持有模型提交、接入或接收锁。回调重新调用 `send` 或等待模型时，不应阻止设备输出区释放。回调失败只重试同一稳定 output_id，不重跑 EX。
- [ ] **帧输出。** V6.1 新 profile 中，具有 frame ID 和帧内位置的新接口允许不同帧交错，单帧的所有 W 项交接完成后才建立相应 FRAME_OUT 完成事实；不带帧 ID 的旧接口按帧连续输出。ACK 译码阶段绑定 FrameRef、槽世代和资格 token；已消费帧的陈旧动作不转投其他帧，旧重发及旧完成不可恢复资格。宿主 FRAME_OUT 接收后的控制记录按逻辑顺序导回设备供后续资格判定；业务 ACK 与输出接收确认是独立协议。旧 profile 按其对应版本的完成及资格契约恢复和验证。
- [ ] **值与条件。** 每次调用结果、发布条件和独立锁存载荷属于该调用的版本，延后交接时不得重新读取最新 q。重复同值结果仍保留独立事件；不发布或正常跳过要推进相应逻辑游标。

## 6. 失败、重试与资源管理

```text
待处理调用
├─ 资源不足／校验失败 → 未公开候选 → 补页、背压或明确失败
├─ 提交前可恢复故障 → 保留调用及已绑定参数 → 显式 retry
├─ 提交后传播／交接故障 → 保留提交身份及游标 → 续接未完成工作
└─ CUDA 致命故障 → 失效整个相关执行域 → 重建上下文／进程 → 持久现场恢复
```

- [ ] **故障分类。** 正常无动作、条件不发布和陈旧 ACK 与执行失败分开；缺页、可恢复执行错误、非法访存／device assert／设备丢失分别报告。检查 kernel launch 返回、依赖 stream 的 event 及后续 CUDA API 错误；正常输入拒绝使用设备诊断记录，而不是会污染上下文的 device assert。event 的 not-ready 是等待状态。
- [ ] **预留与提交。** prepare 阶段计算并完整预留写集、结构变更、事件队列、后继、输出和候选页；禁止在已公开提交后才发现一部分下游载荷无法存放。失败时只释放未公开候选，原 root、身份、事件和已接纳输入继续有效。追加输入区独立于事务根，安装旧根不能覆盖并发接纳。
- [ ] **成员账本。** 每个逻辑执行组记录成员的未开始、已绑定、已提交、失败保留、依赖阻塞及传播进度。非致命失败只阻塞受影响依赖；其他无冲突成员可完成，组状态报告 partial，并允许无关后续工作推进，不能等待整个实例“全部成功”。`step` 对应一个逻辑执行组，部分失败时返回部分完成和故障身份。
- [ ] **显式重试。** 保留同一调用、帧身份、EX／程序版本、已锁存输入及已实际绑定的 q_seed、资源描述和输出身份；重试不排到队尾，不重读已绑定输入。未开始 EX 的普通来源仍在逻辑执行时绑定，不能因故障现场保存而提前冻结。提交前可以使用固定参数重算，提交后只续接未完成传播／交接，避免重复提交和发布。
- [ ] **致命故障。** CUDA 上下文出错后，不能读取失效显存或根据设备完成位推断成功；停止相关 stream、标记执行域无效，由监督器重建进程或 CUDA 上下文。仅以故障前已确认、并在持久模式下保存的连续提交前缀、检查点和日志重建，无法证明的工作据其状态重放或报告缺口。普通内存模式不承诺进程崩溃后无损。

## 7. 快照、持久日志与恢复

### 一致快照

```text
插入输入接纳屏障 F
├─ 完成本组约定的提交与传播，冻结逻辑版本根
├─ GPU 固定／pin 页面和各持有版本
├─ 保存 applied_frontier 与 accepted ≤ F 未应用载荷
├─ 快照 stream 等待提交 event，异步复制受保护旧页
├─ 后续运行写入时复制页面，不覆盖冻结视图
└─ 写临时文件 → 校验／同步 → 原子发布清单 → 同步目录
```

- [ ] **完整现场。** 保存逻辑结构和初值、状态槽与版本、程序和 EX 版本、连接及触发订阅、设备队列和已选调用、参数绑定、事务内部结果引用与创建描述、各触发模式未齐或剩余 token、槽／块世代和分配高水位、模块帧／资格、输出游标与 outbox、SCC 预算、组水位、输入输出身份和持有关系。设备指针、CUDA stream/event 以及可重建索引不序列化为逻辑身份。
- [ ] **输入切点。** 保存 `applied_frontier` 和 `accepted_frontier=F`；已接纳未应用的数据，即使仍在 pinned 区或 H2D 中，也必须由宿主不可变载荷／设备记录或持久日志引用完整保存。传输与切换状态以 input_id 去重，恢复不重复形成事件；F 之后的数据不混入本快照。
- [ ] **页面保护。** 由设备协调器在发布快照 ticket 前 pin 根及可达页面。快照 stream 等待根提交事件；后续写入使用 COW，新旧页都保留到执行读取者、快照 D2H 和其他持有者结束。不能先由宿主读取根，稍后再加保护。显存紧张时可分批复制，但每次都读取同一冻结版本。
- [ ] **保存格式。** 普通格式表示约定的一致边界；故障／部分组恢复使用独立 profile，明确未提交调用胶囊、已绑定参数、已提交成员和传播／输出游标。不得将失败任务伪装成普通完整边界。同步临时文件数据和清单、验证完整性后原子发布，并同步目录；只有确认检查点覆盖日志前沿后才能截断 WAL。

### 持久记录与恢复

- [ ] **持久输入。** 耐久模式将请求身份、输入载荷、逻辑接纳顺序、调用／版本及封存前沿记录到 WAL。按所选承诺完成文件同步后才确认 `durable`。落盘后回复前崩溃时，以客户端稳定 request_id 查询或重试：同一 ID 不重复接纳，不同 ID 的相同 bit 仍是独立输入。
- [ ] **提交与输出。** 对已确认 CUDA 完成的提交保存足以重建状态、结构、触发进度、输出意图与有序提交位置的日志或重做包；依赖于此前提交的结果不得越过未持久的因果前缀。耐久输出先取得宿主私有数据，再同步关联提交／outbox 记录，最后对外交接。恢复只重投同一 output_id。
- [ ] **宿主配合。** 外部副作用要实现跨进程恰好一次，接收方必须按稳定 output_id 做去重或提供幂等协议；本运行时单独保证不了任意回调的恰好一次。传输接收确认与帧业务 ACK 分别记录。
- [ ] **隔离恢复。** 先解析并校验格式、指纹、版本、结构、队列／触发现场、世代和载荷所有权，再重建 GPU 页表、索引和设备池；成功后以暂停状态安装。普通恢复不自动执行 EX、不补造事件、不重放已交接输出；故障 profile 根据已提交状态和游标续接。缺失检查点、日志或合法字段时报告缺口，不猜测修复。

## 8. 接口、兼容与验收

### 运行接口

- [ ] `from_structure`、`restore_runtime` 创建新实例或隔离恢复；`send` 接纳后返回输入身份和异步 ticket，并可分别查询 `accepted / device_visible / durable`。
- [ ] `run`、`pause`、`step` 以逻辑执行组为控制单位；`step` 返回完成、空闲、资源等待或 partial failure 等状态，不把 kernel launch 返回当业务完成。`run(max_tasks)` 的预算约束组封存数；单个过大事务使用独立组、补页或明确资源故障，不无限产生空组。
- [ ] `read_output` 或等价异步输出接口按逻辑序提供稳定 output_id 和载荷；`snapshot`、`retry_failed`、资源／诊断查询明确各自 ticket、错误与生命周期。应用回调与执行器锁独立。
- [ ] PyTorch 入口使用 device guard 和调用者 current stream 的 event；内部执行、输入、输出和快照 stream 独立，返回 tensor 前建立调用者 stream 的就绪依赖。内部可变状态不作为用户可任意修改的 tensor 别名直接公开；不凭空声明支持 `torch.compile`、自动求导或其他硬件后端。

### 版本与兼容

- [ ] 新并行设计、帧格式、事务／环／失败协议使用明确新 profile；结构、运行、模块和 CUDA 后端分别版本化。
- [ ] V5 `draft-1` 与 `draft-2-a03-ready` 分别按各自契约校验并执行兼容语义，不能补造缺失参数或改版本名冒称兼容。旧 profile 的原始 EX、来源和引用、初始化、事件及输出语义保留；新 profile 允许已批准的直接输入、独立订阅、内部依赖和依赖并行。
- [ ] V4 原生恢复、可证明无损迁移、仅导入结构新运行分别给出支持矩阵与迁移报告；缺少的输入或事件历史不能通过默认值伪造。
- [ ] 旧 75 任务及六检查点用于对应的旧契约，不与较早 80／87 节点有限标本混作一个 golden。新并行 profile 验证明确的状态版本、因果偏序及外部序列，不要求无条件重现旧串行总序。

### 验收与性能

- [ ] **独立语义基准。** 标量参考执行器独立推导节点和状态版本；覆盖全部合法 EX、显式 self 的 q_seed、重复引用、参数不足、发布条件和 0。旧 profile 比较其原轨迹；新 profile 按已确认的绑定、组边界、提交顺序与可观察结果比较。
- [ ] **事件与资源。** 对 ANY、ALL_LATEST、ZIP、KEYED 检查同源覆盖、重复 key／重复事件、零值、到达组清空、稳定顺序、分页与容量不足；持续缺项导致背压时，确认当前组不等待未来输入且不丢已接纳事件。
- [ ] **异步和冲突。** 对相同的逻辑封存记录和输入前沿，注入不同 block 大小、模板分组、stream 延迟、H2D／D2H 排序和 allocator 复用；检查跨组状态版本、同状态／同物理页写入、bit-packed word 写冲突、输入封存前沿和输出逻辑序。另做真实时间异步接入测试，核对前沿线性化；不能将不同时间到达导致的不同前沿误判为同一重放。正常跳过、条件静默和故障都要释放依赖、推进游标。
- [ ] **事务与模块。** 覆盖事务内前后依赖、资源不足、动态修改／GC、帧宽和块容量、重复帧、跨帧输出、FRAME_OUT 接收、ACK 译码／陈旧动作、环预算与恢复；验证 CPU 输入／GPU 组／宿主接收之间的竞态。
- [ ] **故障与恢复。** 注入提交前后故障、宿主接纳后 H2D 前快照、冻结页同时改写、WAL 同步前后崩溃、回复丢失、outbox 已持久但应用确认丢失，以及设备致命错误。逐一核对 accepted/device_visible/durable 前沿、同一 request_id 和 output_id 的去重、恢复后续算与输出。
- [ ] **CUDA 真实性能。** 在目标 NVIDIA GPU 上测长链短 EX、长 EX、同构／混合模板、高扇出、热点状态、动态增删与持续 I/O；报告端到端吞吐、输入／输出 p50/p99、各阶段耗时、kernel／同步次数、host 往返、峰值显存和补页成本。比较 byte/bitpack、解释器/JIT、常驻/有界执行，不能以单 kernel 时间代替端到端测量。
- [ ] **GPU 专项工具。** 在真实设备执行编译与异步压力，并运行适用的 Compute Sanitizer memcheck、initcheck、synccheck、racecheck；全局内存发布和 packed-word 冲突还需专门压力测试。CPU 参考或静态推导不证明 GPU 内存顺序正确。本方案目前没有 CUDA 环境验证或性能实测，所有勾选项待实现和实际验收。

## 9. 完整性校验与指纹

### 加载和模型校验

- 加载器完整解析注册 profile 中的合法 EX，保留重复操作与原始表达；检测非法残余字符、非法引用、无效常量和输入绑定。兼容 profile 保持其原来的 EX 语法、输入副本、引用下限和全部存活 Q 的引用／DAG 规则；新 profile 按其显式的计算连接、订阅图、状态绑定、数据依赖与环规则分别验证。
- 节点 ID、世代、程序版本、槽／块世代和分配器高水位分别记录。删除最高编号不得倒退历史分配器；旧绑定不能命中新对象。设备紧凑索引超过范围时切换宽索引或明确报错，不截断逻辑编号。
- 无状态与有状态由 profile 的显式结构／状态绑定确定；旧 profile 按 initial_q 分类，输入副本作为来源时仍按其事件型规则处理。程序优化与共享模板不能更改该分类或订阅。
- 新 profile 的 `PARAM`、`VALUE`、`STATE` 和触发声明必须在形成调用时具有明确绑定规则：例如 ANY 的某一种事件不能提供程序必须的另一个事件参数时，模型需明确从何取得该参数或选择合适的收齐模式；加载器不得把缺失值当作 0。编译化简不得静默删除契约要求的来源、可取得性检查或触发订阅。

### 指纹与规范化

- V5 兼容 profile 严格采用其对应版本已定义的规范字节和结构／格式指纹 F、完整运行指纹 M；结构与初值、契约等按旧规则参与 F，运行状态按旧规则参与 M。数组保序，只归一化对应规范允许的默认值，不把任务内 `cause` 误当成根部展示 metadata 排除。
- 新并行、事务、环与失败 profile 各自声明格式修订、规范化规则、哈希算法、字段范围和测试向量；状态版本、触发剩余、输入输出前沿、预算和事务现场须按该 profile 的定义进入完整运行指纹。不得默改旧版本的摘要规则或仅凭摘要替代字段、世代和引用校验。
- 验收应核对：改变当前 q 影响完整运行指纹；改变 EX 或结构影响相应结构与运行指纹；改变纯设备页布局不影响逻辑指纹；保留高水位、队列顺序、key 及输入输出游标后恢复的规范化结果一致。

### 确认状态与验收状态

全文中“已确认”表示会话中用户已批准方案方向及已列具体选择；`[ ]` 是实现和验收进度，供填写结果，并非要求再次批准。任何未来会改变已批准对外行为的新提案应单独标出，不因技术上可行自动生效。本文的 CUDA 结构、伪代码与容量协议均为设计，真实设备编译、内存顺序、故障注入和性能测量尚未执行。
