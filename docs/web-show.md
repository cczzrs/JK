## 3. 执行会话与执行细节

**执行细节（src/cpu.ts）**

`CpuExecutor` 增加了可选的 `trace` 回调。打开时，执行器按执行顺序报告运行日志项，以及下列细节：

- FIFO 的追加与取出（`push`、`take`），注明是哪一层：0 为 thread，k 为第 k 层事务；
- 前置到达登记（`feed`）：记入后的本轮记录、是否到齐；
- 每次到达（`receive`）：是否经整合放行、all 记录、结果（等待、形成节点任务、空 EX 发布或不发布）；
- 每次计算（`compute`）：q_before、q_start、读到的各来源值、每一项运算后的 acc、publish 判定。

这些细节只是观察，不进入运行日志和执行记录，也不改变执行；不打开时没有额外开销。核对：

- 第 10 节模型、十选一、M_INLINE、M_NEST2、M_EXIT 与 300 个随机模型（含批执行模式），共 322 次运行、5453 个处理单元，打开前后的执行记录完全相同；
- 只按 `push`、`take` 重建的 thread FIFO，在每个处理单元之后都与执行器实际的 FIFO 相同；每层事务结束时，按细节重建的该层 FIFO 都为空；
- 四项检查照常通过。

**会话（session.ts）**

- 一个会话包装一个 `CpuExecutor`，使用默认选项：不按批执行，事务上限取 `TX_LIMITS`。重载、执行运行脚本时新建会话。输出观察由模型的 output 决定（§8.1），页面只显示，不修改。
- 每次调用 `step()` 处理一个处理单元。单步或播放动画时打开执行细节，把单元分成若干步（每次 `take` 开始一步）：事件单元与节点任务单元各一步；一个事务任务单元包括事务内的每次投递、每个节点任务和每个嵌套事务。跳过动画运行时不记录细节，速度更快。
- 动画、投递编号和“本单元”窗口都直接取自执行细节。页面不再自己推算受整合订阅者，也不再倒推 EX 读到的值。
- 输入：按 §9.1 在处理单元之间追加；一次发送先检查全部入口，再逐条追加。运行脚本按 §9.4 在静止时注入下一批。每次输入都记入会话的输入记录（注入时已完成的处理单元数、路径、是否来自运行脚本）。
- 执行记录：显示只保留最近 120 条；下载取自 `ex.record()`，与 `node tools/reference.ts --script` 的输出逐字节相同。
- 场景只更新 q 被写入过的节点；选中、样式改变时整体刷新。
- 执行出错时（例如事务超过上限，§6.4），执行器停在出错的那一步之前，会话标为“已停止”，不再推进。
- 有多个 thread 的模型由 CPU 后端拒绝（§9.3 第 1 项），页面显示原因。

**播放与时间轴（playback.ts）**

- 页面不调用 `run()`，因为它超过 10 万个单元会抛出异常（README C3）。播放按帧调度：
  - 跳过动画时，每帧最多 128 个单元，时间预算为 4 ms × 速度，界面一帧最多刷新一次；
  - 不跳过时，每个单元播放一段动画；事务等多步单元在步数不超过 60 时逐步播放，每步 0.45 秒（除以速度），否则整个单元一起显示。
  - 一次播放处理到 10 万个单元就暂停。这是页面的调度预算，不是规则。
- 时间轴：“后退一步”和“跳到单元”从初值重新执行到目标单元，输入按记录的位置重新注入。执行是确定的，所以不需要快照。继续前进时，记录的输入照原位置重放；手动发送新的输入会让时间轴从当前位置分叉。

## 5. GPU 后端与共用设备

- 页面用 `src/gpu/backend.ts` 的 `requestDevice()` 取得一个设备，由 `gpu-device.ts` 保存：
  - three 的 `WebGPURenderer` 用这个设备渲染，释放渲染器时不销毁设备；
  - GPU 对拍也用这个设备。
- 运行脚本窗口的“GPU 执行并对拍”（`gpu-run.ts`）：
  1. 在 GPU 上从初值整段执行 N 个实例；同一模型的 GPU 管线缓存复用；
  2. 同时在 Worker 中用 CPU 后端算出参考记录，不阻塞页面；
  3. 逐字节比较，显示结果、耗时和调度次数，并可下载 GPU 的执行记录。
- 浏览器没有 WebGPU 时：3D 场景改用 Canvas 2D 软件渲染，GPU 对拍报告取不到设备。
- 尚未实现（见第 8 节）：
  - 把当前 CPU 现场交给 GPU 继续执行（需要快照模块）；
  - 页面直接读取 GPU 状态缓冲区；
  - GPU 单步。

  1. CDN：`https://cdn.jsdelivr.net/npm/three@0.180.0/`（three 官方文档推荐的加载方式，版本与 package.json 相同）。`boot.ts` 先用 HEAD 请求探测 `build/three.webgpu.js`，3 秒内取不到就换下一个；
  2. 本机副本：`tools/server.ts` 的只读路由，只提供以下两个目录中的 `.js` 文件，其余 `node_modules` 仍不提供：
     - `/vendor/three/build/`
     - `/vendor/three/examples/jsm/`
- 地址加 `?three=local` 时只用本机副本。
- `boot.ts` 选定来源后写入 import map（映射 `three`、`three/webgpu`、`three/tsl`、`three/addons/`），再载入 `main.ts`。动态写入 import map 需要浏览器支持多个 import map（Chrome 133 起）；只在本机 Chrome 上核对过。
- 用 CDN 时，three 的约 3.3 MB 由浏览器从 CDN 取得并缓存；页面其余文件仍由本机服务提供。

## 7. 页面约定

- 模型检查用 `src/model.ts`：不合规的模型（包括带 `queues` 的旧格式）列出全部违规后拒绝加载，当前模型保留。
- 输入入口只能是根 JKS 登记的 `trigger.any=[]` 成员（§3.2）。
- 页面只用 JKRD7 的术语：thread、事件 FIFO、任务 FIFO。
- 换模型时保留当前的布局模式，与布局按钮一致。
- 网络概览的元数据显示 JKM 的 jkm、version、threads、input、output 和根 JKS（§8.1）。
- 浏览器存储键为 `jk.show.desktop`、`jk.show.network-styles`、`jk.show.choices`，只保存展示偏好。
- 脚本自己创建的元素只有两类，都不是页面标记：`boot.ts` 写入的 import map 脚本（必须在模块解析之前写入）；渲染用的 canvas（渲染器的画布、标签图集与动画标记的离屏画布）。其余元素都写在 HTML 中或由模板复制（TypeScript.md 第 4 节）。

## 9. 验收

`node tools/show.ts [--write-report]` 启动本机 Chrome 打开展示页，再由页面中的 `verify.ts` 通过页面控件执行以下案例。期望值都由命令行用 CPU 后端算出。

| 类别 | 案例 |
| --- | --- |
| 运行脚本，跳过动画 | §9.4 的十选一脚本（附带 GPU 64 个实例对拍）；第 10 节的 6 个模型，每个输入单独一批，再全部输入一批、首个输入一批，输出观察取各模型的 output（附带 GPU 2 个实例对拍） |
| 逐单元动画 | M_FLOW |
| 逐批发送信号、逐个单步 | M_TX、M_SYNC、M_NEST：每个单元的步数与执行细节一致，本单元窗口列出的步数正确 |
| 时间轴 | 十选一：跳到中间、后退一步、再跳回终点，q 与执行记录都与 CPU 相同 |
| 渲染降级 | M_NEST 在 Canvas 2D 渲染下运行，再恢复 WebGPU |
| 图片转输入 | M_REG：8 个像素的黑白图生成 8 批输入后运行 |
| 事务上限 | M_EXIT（`always_changed`）停在事务步数上限之前，显示“已停止” |
| 模型检查 | 旧格式模型被拒绝，当前模型保留 |
| 布局与 JKS | 十选一：六种布局都完成；选中 JKS 显示详情，场景有 JKS 边界框 |
| 批执行 | 十选一：勾选批执行运行 §9.4 脚本，执行记录与串行相同（6 批，每批 4 个节点任务） |
| 环与退出节点（每个执行案例都核对） | 场景中“出”标记的个数等于模型的退出节点数；选中退出节点时节点详情列出所在的环 |
| GPU 结果（每个 GPU 对拍案例都核对） | 切到“GPU 结果”后，q、场景的 q 与输出列表的行数都与 CPU 后端结束时一致；切回后是原来的会话 |
| 输出窗口（每个执行案例都核对） | 输出数据格式及列表：每条输出的行数与最后一行；不勾选切片记录时每行只有到达的成员；每个 output 组作触发组时的行数（切片与真实运行），真实运行下“全部输出数据”只剩触发的成员。输出渲染：kara 之后为 0 行，全部渲染后等于输出次数；十选一按 done 组触发时的 ASCII 文字。场景动画：按输出格式与切片记录的取舍（保留的输出条数与成员） |

每个执行案例检查以下各项：

1. 页面导出的执行记录与 CPU 后端逐字节相同。
2. 页面显示的状态与 CPU 后端运行结束时一致：处理单元数；静止后两个 FIFO 都为 0，运行状态为“静止”（事务超限的案例为“已停止”）；输出次数；执行记录窗口的最后一行；节点详情中每个 JKI 的当前 q。
3. 场景显示的每个 JKI 的 q 与写入次数，以及观察点个数，与 CPU 后端一致。
4. 发送信号之后，事件 FIFO 显示的项数和首项正确。
5. GPU 对拍报告“逐字节相同”。

2026-11-11 在本机（Chrome 157，Apple GPU）18 项全部通过，渲染后端为 WebGPU。两个复制按钮另用一次性探针在独立的无界面 Chrome 157 中核对：以真实鼠标事件点击，读回的剪贴板内容与列表一致（剪贴板权限由调试协议授予；日常 Chrome 中 localhost 页面默认可写剪贴板，没有直接核对）。

这些检查通过，只说明在本机已核对的范围内页面与规则一致。不说明快照恢复、多 thread、其他浏览器或其他 GPU 已经验证。
