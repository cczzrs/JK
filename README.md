# JK · JKRD7

本项目只维护 **JKRD7（7.0.0）**：JKI／JKS 的设计规则、已批准的模型示例、静态检查，以及按规则实现的执行器。不兼容、不维护此前版本。

唯一规则入口是 [JKRD7.md](JKRD7.md)。尚未确定的选择集中在 JKRD7 §9.3。全部代码用 TypeScript 编写。执行器有两个后端：

- **CPU 后端**（默认）：JKRD7 的串行参考语义，是判断对错的基准；
- **GPU 后端**：在 WebGPU 上同时执行许多实例，执行记录必须与 CPU 后端逐字节相同。

两个后端都只执行单 thread 模型。

## 设计要点

- **JKI**：每个节点保存 q；trigger 为 any 或 all；EX 由 J（AND）、K（XOR）组成，在执行入口读取来源的 q；publish 有七种模式。通知不携带值。
- **JKS**：members 递归保存完整的 JKI 与子 JKS；跨层引用写绝对路径。trigger 登记本结构的前置成员，按类型整合它们的通知：any 不整合，all 到齐后同步放行，transaction 到齐后形成事务任务，transaction_any 每条通知形成一个事务任务。
- **事务**：范围是除前置成员以外的全部成员；事务内按 publish 结果沿连接传播；发往范围外的通知在结束时统一提交；不设失败与回滚；多个事务任务按任务 FIFO 顺序逐个执行。
- **执行模型**：一次处理一个单元；事件优先；同一通知按订阅者绝对路径的顺序投递。任何并行实现对同一运行脚本必须产生与串行参考相同的执行记录；JKRD7 §7.5 给出了可以直接并行的任务批。
- **运行脚本与快照**：运行脚本规定输入批与输出观察，执行记录按串行顺序逐条列出；快照保存两个处理单元之间的全部运行状态。
- **JKM**：模型封装，包含版本、thread 声明与根 JKS。

## 核对

需要 Node 26（[.node-version](.node-version)），首次运行前执行 `npm install` 安装类型检查用的开发依赖。GPU 后端还需要本机装有 Chrome。

```sh
npm run typecheck
node tools/validate.ts
node tools/reference.ts
node tools/gpu.ts
```

- `npm run typecheck`：TypeScript 类型检查。
- `tools/validate.ts`：静态检查。范围包括 JKRD7 中的 JSON、模型附件、正例与负例、待适配附件的 JSON 语法、本地链接和索引。
- `tools/reference.ts`：用 CPU 后端执行 JKRD7 第 10 节的模型与十选一附件，核对 §11.2 的验收案例。案例包括批执行模式、运行脚本和快照。
- `tools/gpu.ts`：以无头模式启动本机 Chrome，在 WebGPU 上执行 GPU 后端，并与同一页面里的 CPU 后端逐字节对拍。
- 加 `--write-report` 时更新 `reports/` 下的报告。
- 用 `--script <运行脚本>` 输出 JKRD7 §9.4 的执行记录，供逐条比对：
  - `node tools/reference.ts`（CPU）可加 `--batch`、`--start <快照>`、`--save <快照>`；
  - `node tools/gpu.ts`（GPU）可加 `--start <快照>`、`--save <快照>`。
- 运行 `npm run serve` 后，可以在浏览器中打开 GPU 对拍页面手动查看。

这些检查通过，只说明在本机已核对的范围内两个后端与规则一致。其他浏览器、其他 GPU、恢复流程和多 thread 调度尚未验证。

### 一、规则层面（需要决定）

| 编号 | 问题 | 现状与证据 | 建议 |
| --- | --- | --- | --- |
| R1 | 经 JKS all 整合的通知环不算“纯通知环” | §6.2 只拒绝连接都不经整合的环。探测：G1 登记 all=[Q2]，Q2→Q3→Q2，Q2、Q3 都是 any、空 EX、always。只有一个前置，所以每次到达都立即到齐、立即放行，环只由事件组成。结果是静态检查放行，运行永不静止，节点任务永远得不到执行，后果与纯通知环相同 | 扩充 §6.2 的定义：经 all 整合的连接，如果该 all 登记的全部前置都在这个环所在的强连通分量内，也视为不经整合；或者明确把这类环交给运行时的步数上限 |
| R2 | 从未静止的快照开始运行时，第一批输入何时注入 | §9.4 要求每批“在模型静止时”注入。两个后端载入快照后都直接注入第一批再运行。探测：M_TX 中途快照（任务 FIFO 中有一个事务任务），再注入 G1.Q10，第一条记录就是 inject，随后先投递新事件，后执行原有的事务任务 | 规定载入快照后先运行到静止，再注入第一批；或者规定运行脚本只能从静止的快照开始 |
| R3 | 快照依赖观察配置（observe） | 事务提交时，被观察的来源即使没有范围外接收者，也要留一项 `{"to": [], "out": true}`，没有被观察就不留。所以同一时刻、不同 observe 得到的快照不同。探测：M_TX 用未观察 Q101 时取的快照，改为观察 Q101 后继续，输出从 2 次变成 1 次。可见 §9.5 中“结果与不中断的运行相同”只在 observe 相同时成立 | 在 §9.5 写明“快照只能用同一 observe 继续”，并在快照中记录 observe（例如 watch 列表），载入时核对 |
| R4 | §9.5 对队列项的约束不完整 | 目前只要求 to 中是 JKI 路径、tx 的 prereqs 是该 JKS 的前置。没有要求：to 中的每个接收者是 source 的订阅者；事务任务的 prereqs 来自 transaction 或 transaction_any 登记；transaction 列出该登记的全部前置且不重复；transaction_any 恰好列出一个前置 | 在 §9.5 补上这些约束（代码对应 C1） |
| R5 | §9.4 的批能否为空 | JKRD7 没有说批必须非空，但静态检查拒绝空批 `[]`；GPU 接口内部又用空批表示“不注入，只运行到静止” | 规定是否允许空批；允许时，含义是“不注入，只运行到静止”（与 R2 一起定） |
| R6 | §2 第 2 条“bit 只能是整数 0 或 1” | JavaScript 解析 JSON 时无法区分 `1.0` 与 `1`，所以写成 `1.0` 的 q 会被接受；原 Python 版会拒绝 | 接受这一限制并写进 TypeScript.md；或者改为检查 JSON 原文 |

JKRD7 §9.3 原有的待补充项仍未确定：

1. 同一 JKI 被多个 JKS 登记；
2. ack 等用途的专门行为；
3. 多个 thread 之间的调度；
4. 快照的保存时机与恢复流程；
5. 输出接入的接口；
6. 工厂模块。

### 二、执行器代码（按规则修正，动手前请确认）

| 编号 | 问题 | 证据 | 建议 |
| --- | --- | --- | --- |
| C1 | 快照检查会放行不合法的队列项，两个后端的表现也不同 | 第一种：to 中写了不是订阅者的节点。CPU 会在 trigger_all 记录的下标 -1 处写值，结果静默出错；GPU 编码时报错。第二种：事务任务的 prereqs 多于事务登记的前置数（例如列出 all 登记的 3 个前置）。CPU 照这些前置执行事务；GPU 每项只留了 1 个前置的位置，执行时会读到下一项的字：实际读到 Q2、Q2、Q1，CPU 则是 Q2、Q3、Q4 | checkSnapshot 补上 R4 的约束；GPU 编码另加越界保护 |
| C2 | 一次事务提交的项很多时，CPU 后端崩溃 | 一个事务提交 10 万项时，`Fifo.push(...展开)` 栈溢出（RangeError） | 改成逐项追加 |
| C3 | 两个后端的步数上限不一致 | CPU：每次 run() 最多 10 万个处理单元，超出时抛异常，命令行打印堆栈，而且不能配置；一个扇出 20 万、本来会正常结束的模型也因此失败。GPU：每批最多 100 万个微步，报错码 6，并交回已有记录。两者的计数单位、默认值、报错方式都不同，同一个不终止的模型交回的记录条数也不同。探测：R1 的环在上限都设为 2000 时，GPU 交回 2000 条记录，CPU 有 2002 条 | 统一为“每批处理单元上限”，默认值相同，可在命令行配置；两边都交回已产生的记录和同一种错误信息 |
| C4 | 没有统一的执行器入口 | executor.ts 中只有 CPU 的 runScriptCpu，`Backend` 类型没有被使用；GPU 要另外调用 GpuExecutor；命令行也分成 reference.ts 与 gpu.ts 两个 | 增加 `runScript(script, model, { backend: "cpu" \| "gpu", … })`，默认用 CPU；命令行增加 `--backend` |
| C5 | GPU 只能在运行结束时取快照 | 没有“执行 n 个处理单元后停下”的接口，无法在 GPU 上复现 CPU 的中途快照 | 需要时，增加按处理单元暂停的功能 |
| C6 | GPU 的容量要手动设定 | 默认各 64 项：不够时报错，过大又浪费显存 | 按模型估计容量（WebGPU.md 第 4 阶段） |
